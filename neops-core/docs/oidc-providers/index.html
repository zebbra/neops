    OIDC providers

    How to set up an identity provider for Neops so that users can log in through it and arrive with the right roles. The first part is what every provider has to deliver; then there are step-by-step sections for Keycloak, Microsoft Entra ID and Okta, short notes for authentik and Google, and a checklist for any other provider.

    What a role grants once it arrives is in Permissions and roles; how core implements the login is in OIDC authentication. OIDC login needs the quay.io/zebbra/neops-core image: the neops-cms-free and neops-cms images do not contain it.

    What every provider has to deliver

    The flow, and where the provider fits

    sequenceDiagram
    participant B as Browser
    participant W as Web client
    participant C as Core
    participant I as Identity provider
    B->>W: open login page, pick the provider
    W->>C: /auth/oidc-login/<provider_id>/
    C->>I: authorization-code request (openid profile email)
    I->>B: sign-in
    B->>C: /accounts/oidc/<provider_id>/login/callback/?code=
    C->>I: token request (client secret), userinfo
    Note over C: checks email_verified, syncs profile and roles
    C->>W: one-time code
    W->>C: exchangeOidcCode
    C->>W: Neops access and refresh token

    The provider’s tokens stay inside core: core reads the ID token and the userinfo response, never the access token, and the browser only ever holds Neops tokens. Anything the provider puts into the access token alone is invisible to Neops.

    URLs to register

    What Value
    Redirect (callback) URI <CMS_URL>/accounts/oidc/<provider_id>/login/callback/, trailing slash included
    Post-logout redirect URI the web client’s /login, i.e. core’s NEOPS_FRONTEND_LOGIN_URL (<WEB_URL>/login)

    Core builds the callback from the Host header of the request it receives, so a reverse proxy in front of core must keep Host unchanged. It uses https unless ACCOUNT_DEFAULT_HTTP_PROTOCOL=http, which a plain-HTTP evaluation setup must set (the Compose deployment derives it from the web URL). On logout core sends the browser to the provider’s end_session_endpoint with client_id and post_logout_redirect_uri, but without id_token_hint, because it never stores the provider’s tokens; some providers show a “do you want to log out” page because of that.

    Who gets an account

    Every person the provider lets sign in to the Neops client gets a Neops account at their first login, with no further approval. Restrict who may sign in at the provider (the assignment settings below), because an account without any role still holds the element defaults, and some of those are open by default (see the warning in Permissions and roles).

    Claims

    Claim Required What core does with it
    sub yes the identity of the account; a different sub is a different user
    email yes, except under the trust opt-out kept in sync with the user’s address; links to an existing user (below). Under the opt-out a login without an address is let through and creates a user without one
    email_verified yes, boolean true every login without it is refused (?error=email_not_verified), new and existing users alike. The string "true" is not enough
    preferred_username no the username of a new user. Without it the part of email before @, without that oidc-<first 8 of sub>; if that name is taken, one built from the user’s names and address. Never changed afterwards
    given_name, family_name no first and last name, updated at every login when present
    roles no, but see below the user’s Neops roles

    A provider that cannot emit email_verified (Entra, authentik from 2025.10 on) needs "trust_email_without_verification": true in its settings, which lets its logins past that check.

    Matching existing users by address. When the provider marks the address verified in its userinfo response and the address belongs to an existing Neops user, the login is linked to that user and logs in as them from then on, superuser and roles included. That is how a local account moves to single sign-on, and it is also how anyone the provider vouches for with that address takes the account over. Before turning OIDC on, make sure every local account, the installation’s admin user above all, either belongs to the same person in the provider or has an address no provider identity carries.

    Linking follows the provider’s own email_verified in userinfo, not the trust opt-out:

    • A provider that sends no email_verified at all (Entra) is never linked. A login whose address already belongs to a Neops user then stops on a sign-up page of the CMS instead of returning to the web client.
    • A provider under the opt-out that sends email_verified: true for some users is still linked for those users.
    • A provider that sends email_verified as a string is linked even for "false". Core refuses such a provider unless the opt-out is on, so never use the opt-out for a provider that sends the claim as a string: it would link unverified addresses to existing accounts.

    For a new user, core takes the username and names from the userinfo response alone when it fetched one (the default), and from the ID token otherwise. For everything else, including roles and the email_verified check, it merges both, userinfo winning where it has a value.

    Roles

    Core looks for roles in this order, in the merged ID token and userinfo:

    1. resource_access.<client_id>.roles, Keycloak’s shape for client roles, where <client_id> is the client ID Neops is registered with;
    2. a top-level roles array of strings, the shape Entra, Okta (as configured below) and most other providers can produce.

    groups is not read. A provider that only sends a groups claim delivers no roles.

    What arrives Effect on the user’s roles
    A role list the user has exactly these roles. Missing ones are created in Neops, roles not in the list are taken away
    No role claim at all left as they are, with a warning in core’s log. New users get none
    resource_access without an entry for Neops’ client ID all taken away
    A claim of the wrong type (roles not a list, .roles a string) all taken away
    A list with non-strings or names over 255 characters those entries are skipped, the rest apply

    Consequences to plan for:

    • The provider decides as soon as it sends roles. Roles assigned by hand in Neops to a user whose token carries roles are replaced at the next login. Either manage roles in the provider, or send no role claim and manage them in Neops; mixing the two does not work.
    • Names must match exactly, including case. A role the provider sends is created in Neops with no grants, so give the role its grants under its exact name, before or after the first login.
    • A name can grant any existing role. A provider role or group named like the seeded admin role (admin unless NEOPS_ADMIN_ROLE says otherwise) makes its members Neops administrators. Do not send names of privileged Neops roles you did not mean to hand out, and treat whoever administers the provider’s roles and groups as a Neops administrator.
    • Providers usually send no claim once a user’s last role is gone, which leaves the user’s Neops roles as they were. Check this for your provider on a user without roles (Keycloak’s Evaluate, Okta’s Token Preview).
    • Changes reach Neops only at an interactive login. Refreshing a session never asks the provider again, and a session can be refreshed indefinitely. To take someone’s access away, deactivate the user in Neops (Users in the admin site); see When a change takes effect.
    • A role sync never touches is_superuser or is_staff. Admin-site access stays a local decision.

    Telling core about the provider

    A provider is one Social application row in core (allauth’s SocialApp, provider openid_connect), seeded at start from the JSON file named by AUTH_PROVIDERS_CONFIG_PATH:

    {
  "providers": [
    {
      "provider_id": "entra",
      "name": "Microsoft",
      "client_id": "<client id>",
      "secret": "<client secret>",
      "settings": {
        "server_url": "https://login.microsoftonline.com/<tenant id>/v2.0/.well-known/openid-configuration",
        "oauth_pkce_enabled": true,
        "trust_email_without_verification": true
      }
    }
  ]
}
    • provider_id appears in the callback URL and must stay stable once registered. name is the label of the login button. Several providers give several buttons.
    • server_url is the discovery URL; an issuer URL without /.well-known/ also works.
    • Optional settings keys: scope (default ["openid", "profile", "email"]), oauth_pkce_enabled (default off; turn it on, every provider here supports it), token_auth_method (client_secret_basic or client_secret_post), auth_params (extra authorization parameters such as prompt), fetch_userinfo (default on).
    • The file only inserts. A provider already in the database keeps its row when the file changes, a new client secret or discovery URL included. Apply a change with manage.py seed_oidc_providers --force, or edit the row in the admin site under Social applications.

    With the Compose deployment, NEOPS_OIDC_* in .env produce this file for one provider; see its OIDC scenario documentation. Compose does not set oauth_pkce_enabled or scope, and a changed value in .env, such as a renewed client secret, takes effect only after ./neops compose -- exec cms python manage.py seed_oidc_providers --force. Password login is off while OIDC is on, unless NEOPS_LOCAL_LOGIN_ENABLED=true; the admin site’s own login at /admin/ is unaffected.

    Keycloak

    Keycloak 26. The Compose deployment’s bundled Keycloak overlay creates all of this for you (realm neops, client neops-auth); these steps are for your own Keycloak.

    Realm

    1. Realm settings → Login: keep User registration off, unless everyone who can register should get a Neops account. A brokered identity provider with Trust Email on passes its users’ addresses on as verified; only broker providers you trust for that.

    Client

    1. Clients → Create client. Client type OpenID Connect, a Client ID such as neops-auth, Next.
    2. Capability config: Client authentication On (a confidential client), Standard flow on. Next.
    3. Login settings: Valid redirect URIs <CMS_URL>/accounts/oidc/<provider_id>/login/callback/, Valid post logout redirect URIs <WEB_URL>/login. Save.
    4. Credentials tab: copy the Client secret.

    Roles

    1. In the client, Roles tab → Create role, one per Neops role, named exactly like it.
    2. Assign them: Users → the user → Role mapping → Assign role, filter by clients, pick the roles, Assign. Or assign them to a group under Groups → the group → Role mapping; members inherit them.

    Put the roles where Neops can read them. Keycloak’s built-in client roles mapper writes resource_access into the access token only, so without this step every user arrives without roles.

    1. In the client, Client scopes tab → <client id>-dedicated → Configure a new mapper (or Add mapper → By configuration) → User Client Role:
    2. Client ID: the Neops client
    3. Multivalued on
    4. Token Claim Name: resource_access.${client_id}.roles
    5. Claim JSON Type: String
    6. Add to ID token on, Add to userinfo on
    7. Check it: client → Client scopes → Evaluate, pick a user, and look for resource_access.<client id>.roles in Generated ID token and Generated user info.

    Prefer this dedicated mapper over switching on Add to ID token on the realm-wide roles scope’s client roles mapper. The realm-wide one also emits other clients’ roles under resource_access, and a user who holds roles on another client but none on Neops’ then arrives with resource_access lacking Neops’ entry, which takes all their Neops roles away.

    Email

    1. Keycloak sends email_verified from each user’s Email verified switch. A user created by an administrator has it off: switch it on in the user’s details, or turn on Realm settings → Login → Verify email so users confirm their address. Do not use the trust opt-out for Keycloak.

    In core’s JSON, server_url is https://<keycloak>/realms/<realm>/.well-known/openid-configuration.

    Microsoft Entra ID

    App registration

    1. Microsoft Entra admin center, as at least Application Developer: Entra ID → App registrations → New registration. A name, Supported account types Single tenant only, Register. Note the Application (client) ID and the Directory (tenant) ID. Single tenant matters: any other setting lets users of other tenants, or personal Microsoft accounts, sign in and get Neops accounts.
    2. Authentication → Add Redirect URI → Web: <CMS_URL>/accounts/oidc/<provider_id>/login/callback/. Then add a second Web redirect URI, <WEB_URL>/login: Entra only accepts a post-logout redirect that is also a registered redirect URI. Leave the front-channel logout URL empty. Entra requires https for every redirect URI except localhost.
    3. Certificates & secrets → Client secrets → New client secret. Copy its Value (not its ID); it is shown only on this page. A secret lasts at most 24 months, and login stops working the day it expires, so put the date in a calendar (and see Telling core about the provider for applying the new one).
    4. Token configuration → Add optional claim → token type ID → email → Add, so the address is also in the ID token core reads at later logins. A user without a mail address in Entra still logs in and gets a Neops account without an address, named oidc-…; only Assignment required (step 7) keeps such users out.

    The default API permissions (Microsoft Graph User.Read, delegated) are enough; Neops needs no admin consent.

    App roles

    1. App roles → Create app role, one per Neops role:
    2. Display name: free text, shown in Entra only
    3. Allowed member types: Users/Groups
    4. Value: the Neops role name, exactly; this is what Neops receives. It cannot contain spaces, so Neops roles that come from Entra cannot either.
    5. enable it, Apply.
    6. Entra ID → Enterprise apps → the same app → Users and groups → Add user/group: pick users or groups and a role, Assign. Assigning to groups needs Entra ID P1 or P2, and nested groups do not count.
    7. Enterprise apps → the app → Properties → Assignment required? Yes. It defaults to No, under which every member of the tenant, guests included, can sign in and gets a Neops account.

    Entra puts the assigned values in the ID token as a top-level roles array, which Neops reads. A user with no assignment gets no roles claim, so their Neops roles stay as they were; with Assignment required on, they also cannot start a new login. An open Neops session is not affected by either: deactivate the user in Neops to end it.

    Use app roles, not the groups claim: Neops does not read groups, and Entra emits group object IDs there, replaces the list with a reference above 200 groups, and differs between tenants.

    Core settings

    1. server_url: https://login.microsoftonline.com/<tenant id>/v2.0/.well-known/openid-configuration. Use the tenant ID, never common or organizations: their discovery document names an issuer with a {tenantid} placeholder, which no real token matches, so login fails, and they would admit users of other tenants.
    2. "trust_email_without_verification": true: Entra never sends email_verified. Because it sends none, Entra logins are never linked to existing Neops users by address (see Matching existing users): a Neops user whose address an Entra user also has cannot log in through Entra until that local account is removed or given another address.
    3. Usernames: Entra’s userinfo response has no preferred_username, so a new user’s username is the part of their email before @.

    Okta

    App integration

    1. Admin Console: Applications and Resources → Applications → Create App Integration → OIDC - OpenID Connect, Web Application, Next. (Older consoles name the first menu Applications.)
    2. Grant type Authorization Code; Sign-in redirect URIs <CMS_URL>/accounts/oidc/<provider_id>/login/callback/; Sign-out redirect URIs <WEB_URL>/login. Under Assignments, limit access to the groups that should log in: allowing everyone gives every user of the organization a Neops account. Save.
    3. General → Client Credentials: copy the client ID and secret.

    Roles as a roles claim. Okta delivers group memberships, under the name groups by default, which Neops does not read. Rename the claim to roles and filter it to the groups that are Neops roles, so the group names become Neops role names. Anyone who can create a group matching the filter can then hand out that Neops role, so choose a filter only administrators’ groups can match. Where the claim is set up depends on the authorization server:

    • Custom authorization server (recommended; default on the Integrator Free Plan, others need API Access Management): Security → API → Authorization Servers → the server → Claims → Add Claim: Name roles, Include in token type ID Token, Always; Value type Groups; Filter, for example Starts with neops-; Include in any scope; Create. Check it on the server’s Token Preview tab. The server needs an access policy and rule that allow the app. Okta fails the login when the filter matches more than 100 groups.
    • Org authorization server (every plan): the app → Sign On → OpenID Connect ID Token → Edit: Group claim type Filter, claim name roles, a filter as above, Save. Okta adds it only when the login asks for the groups scope, so core’s provider settings need "scope": ["openid", "profile", "email", "groups"]. The Compose deployment does not expose scope, so with Compose use a custom authorization server.

    Core settings

    • server_url: https://<okta domain>/oauth2/<authorization server id>/.well-known/openid-configuration (/oauth2/default/… for the default server), or https://<okta domain>/.well-known/openid-configuration for the org authorization server.
    • Okta sends email_verified for the user’s primary address; no opt-out needed.

    Other providers

    • authentik can send roles: add a Scope Mapping (Customization → Property Mappings) whose expression returns {"roles": [...]}, attached to a scope Neops requests such as profile. Since authentik 2025.10 the email scope sends email_verified: false unless addresses are verified, so either verify them in an email stage or use the trust opt-out. With the opt-out, anyone an enrollment flow lets register gets a Neops account under an address nobody checked: keep enrollment off for the Neops application, or verify addresses.
    • Google (Workspace sign-in) sends email_verified but has no way to add a roles claim: logins work, and roles are managed in Neops. Set the OAuth consent screen’s user type to Internal. With External, every Google account can sign in, including a personal Google account registered with a work address, which then matches that person’s Neops account.

    Checklist for any provider

    1. A confidential client using the authorization-code flow, with the two URLs from URLs to register, and PKCE on.
    2. Only the people who should use Neops can sign in to that client.
    3. The ID token or userinfo carries sub, email and a boolean email_verified: true. Use trust_email_without_verification only for a provider that sends no email_verified at all and whose addresses only your administrators can set; never for one that sends it as a string.
    4. If roles should come from the provider: a top-level roles array of strings, in the ID token or userinfo (not only in the access token), whose values are the Neops role names, and none of them a privileged Neops role you did not mean to hand out. Otherwise send no role claim at all and assign roles in Neops.
    5. The roles exist in Neops with their grants (see Permissions and roles).
    6. The provider’s discovery issuer equals the iss in its tokens exactly.

    Checking a login

    • After a first login, the user appears in the users of each synced role, in the admin site under Role permissions. Core logs every role change, at WARNING when roles were removed, and logs a warning when a token carried no role claim.
    • A Neops access token carries the result: decode it and look at roles and permissions.
    • A failed login lands on the web client with an error parameter:
    error Meaning
    email_not_verified no email_verified: true and no trust opt-out
    provider_error the provider refused or could not be reached; also an issuer mismatch, such as Entra’s common endpoint
    account_inactive the matching Neops user is deactivated
    (no error; the login stops on a sign-up page of the CMS) the address belongs to an existing Neops user and the provider sent no email_verified, see Matching existing users
    auth_failed / internal_error see core’s log
