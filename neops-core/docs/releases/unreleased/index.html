    Neops Core, next release

    Not released yet. These notes cover lockState, a query that answers a lock’s state without changing it, a retireLock that records a reference as retired when it finds no lock, lockId, which names the lock row each lock answer is about, and an unlockResources that applies its writes only under the lock its caller names.

    Upgrade notes

    A retire with no lock fails until the migrate Job finishes

    Migration 0210_composite_lock_never_held lets core_compositelock.global_lock_id be null, and adds the check only_held_rows_need_a_global_lock: only a row that is not locked may have no global lock. The only such row is the retired row of a reference that never held a lock (see below). The migration rewrites no rows. It takes an exclusive lock on core_compositelock, which blocks reads of the table as well as writes: every lock request, unlock, retire and lockState waits while it is held. It holds that lock for one scan of the table, which validates the check. The table holds every lock row kept since 2.7.0, so the scan grows with the lock history. The migration waits at most 5 seconds for the lock (lock_timeout) behind lock and unlock transactions still open, and fails the migrate Job if it cannot get it, rather than leaving every lock call queued behind it. Rerun the Job; nothing has changed. Until the post-upgrade migrate Job has run, a retireLock that finds no lock row fails with a GraphQL error and changes nothing; every other lock call works.

    Migration 0211 holds a row without a global lock to one shape

    Migration 0211_composite_lock_never_held_is_retired replaces the check only_held_rows_need_a_global_lock with a_row_without_a_global_lock_is_a_never_held_retire: a row may lack a global lock only if it is not locked, is retired, and has neither unlocked_at nor released_by. That is exactly the row a retire writes for a reference that never held a lock. Lock creation reads “retired” from retired_at, while lockState and the admin read “retired without ever being held” from the missing global lock; the database now makes the two agree for every writer, a hand-written repair included. The migration rewrites no rows. It takes the same exclusive lock as 0210 for one scan of the table and waits at most 5 seconds for it (lock_timeout), also when it is reversed. If it cannot get the lock, it fails the migrate Job, which can be rerun; nothing has changed. lock_timeout bounds only the wait for the lock, not the scan: once the migration holds the lock, every lock request, unlock, retire and lockState queues behind it until the scan ends. The scan reads core_compositelock once, sequentially, so it takes as long as the lock history kept since 2.7.0 is large, and prune_lock_history is what bounds that history. Check the table’s size before the upgrade (SELECT pg_size_pretty(pg_table_size('core_compositelock'))) and prune first if it is large. There is no statement_timeout: the check is validated only by finishing the scan, so a timeout would fail the Job again on every rerun without making the upgrade possible. The scan cannot fail on rows written by 2.6, 2.7.0, 2.8.0-beta.1 or this release: before 0210 every row had a global lock, and since then only a retire of a reference with no row writes one without, in exactly this shape. Older pods never change the columns the check reads on such a row. 2.7.0 and 2.8.0-beta.1 release, refresh and re-index only held rows, and leave a retired row alone. A 2.6 pod’s unlock touches only held rows, its admin refresh rewrites a selected row with the values it read and a new expires_at (it knows neither retired_at nor released_by), and its admin unlock and expiry sweep delete rows. If the scan does fail, a row was written by hand. The known source is the 2.8.0-beta.1 admin’s add form, which accepted a lock row without a global lock; this release removes it (see the admin below). Find such a row with SELECT * FROM core_compositelock WHERE global_lock_id IS NULL AND NOT (NOT locked AND retired_at IS NOT NULL AND unlocked_at IS NULL AND released_by IS NULL). No lock request wrote it, so it records no lock of the workflow engine. First delete its links in either case: DELETE FROM core_devicelock WHERE composite_lock_id = N and DELETE FROM core_devicegrouplock WHERE composite_lock_id = N; a row retired without ever being held has none. Then delete the row (DELETE FROM core_compositelock WHERE id = N), or, if it was meant to record a retired reference, give it that shape: UPDATE core_compositelock SET locked = false, retired_at = now(), unlocked_at = NULL, released_by = NULL WHERE id = N. Then rerun the migrate Job.

    Older pods during the rolling upgrade

    This section names the release of the old pods it applies to: 2.7.0 or 2.8.0-beta.1. An upgrade from 2.6 or older passes through 2.7.0’s upgrade notes as well.

    Neither a 2.7.0 nor a 2.8.0-beta.1 pod knows lockId. Such a pod answers a call that sends the lockId argument, or selects lockId or unlockedAt, with a GraphQL validation error, and executes nothing. The operation documents in neops-graphql/graphql/ select these fields for every lockState, unlockResources and retireLock, so every such call from an engine built against them fails on an old pod, not only a guarded one. Finish the core rollout before deploying such an engine (see Workflow engine below).

    A 2.8.0-beta.1 pod takes the same per-reference turn and records a retired reference that has no lock in the same shape, so the 2.7.0 paragraphs below do not apply to it. Its admin still offers an add form for lock rows (see migration 0211 above).

    A 2.7.0 pod that still serves does not take the per-reference turn described below, and it does not record a retired reference that has no lock. A retire with no lock that such a pod serves marks nothing, as in 2.7.0. A 2.7.0 pod reads a reference retired without ever being held as retired: it refuses a lock request with RETIRED, answers an unlock RETIRED with releasedBy: OWNER_UNLOCK, and answers a repeated retire lockExists: true, alreadyRetired: true.

    One interleaving leaves a lock held next to a retired row of the same reference. A 2.7.0 pod starts the first lock request of a reference and has not committed it. A new pod retires the same reference, finds no row, and records it retired. Then the 2.7.0 pod’s request commits. Which of the two rows is the newest depends on when each was inserted, not when it committed, because row ids follow insert order:

    lockState getAndLockResources retireLock unlockResources
    held row inserted first, retired row newest RETIRED lockAlreadyExisted: true with the held lock: its check for a held lock runs before the newest row is read alreadyRetired: true, lockExists: false RETIRED; releases nothing. With lockId naming the held row: LOCK_REPLACED, lockExists: false, lockId the retired row, releasedBy and unlockedAt null although the named lock is the caller’s and still held; releases and writes nothing
    retired row inserted first, held row newest HELD lockAlreadyExisted: true with the held lock LOCK_HELD releases the lock and applies its writes, also with lockId naming it

    Either way the workflow engine has already been told the reference is retired, so it never unlocks it, and the lock stays held until its expiry; a lock the workflow engine takes has none. prune_lock_history never deletes a reference and owner that has a held row, so the devices are not left counted as locked with nothing to release them. Look for such a lock in the admin’s Composite locks list: filter by state “Held” and compare its reference with the retired ones. That finds both orders. Release it with the “Unlock composite locks” action. Only this rolling upgrade can leave a held row next to a retired one: in this release, a lock request and a retire of the same reference take turns, so the row inserted last is also the one committed last.

    Sentry is no longer used

    Core no longer reports errors or traces to Sentry, and the sentry-sdk dependency is gone. SENTRY_DSN, SENTRY_ENVIRONMENT and SENTRY_ENABLE_TRACING are ignored; remove them from your environment when convenient. appSettings.sentry stays in the schema, deprecated, with dsn and environment always null, so frontends built against an older generated client keep passing validation on the login page; the operation documents in neops-graphql/graphql/ no longer select it, and it will be removed in a later release.

    Built-in cleanup tasks follow their settings on every beat start

    Celery beat now applies each built-in cleanup task’s settings when it starts, so the environment, not the Django admin, decides whether the task runs and how often:

    Task Enabled Interval in minutes (default)
    Execution/Log Retention NEOPS_LOG_RETENTION_ENABLED NEOPS_LOG_RETENTION_INTERVAL_MINUTES (1440)
    Fact Cleanup FACT_CLEANUP_ENABLED FACT_CLEANUP_INTERVAL_MINUTES (1440)
    Check Cleanup CHECK_CLEANUP_ENABLED CHECK_CLEANUP_INTERVAL_MINUTES (1440)
    Cleanup Stuck Executions NEOPS_EXECUTION_CLEANUP_ENABLED NEOPS_EXECUTION_CLEANUP_INTERVAL_MINUTES (10)

    Every enabled setting defaults to False. A task that was enabled in the admin while its setting is off still did nothing, so nothing that ran stops. But an interval changed in the admin goes back to the setting’s value, and a task disabled or deleted in the admin comes back while its setting is True, each time beat restarts. Set the variables instead; a change takes effect with the next beat restart. A task moved to a crontab in the admin keeps its crontab and only follows the enabled setting.

    Check Cleanup is new: with CHECK_CLEANUP_ENABLED=True it deletes inactive checks beyond the newest 20 per entity and key. CHECK_RETENTION_MAX_ENTRIES, e.g. device=50,common=10, changes the limit for the types it names. manage.py cleanup_checks --dry-run shows how many it would delete, also while it is still disabled. A type that isn’t one of device, interface, device_group, client and common stops Core from starting. Fact Cleanup no longer fails on facts that a check still references.

    Retiring a reference with no lock

    retireLock records the reference as retired, also when the caller has no lock row for it. That happens when the run’s lock request timed out on the engine’s side and may still be running in core. The retire then inserts a retired row with locked = false and global_lock_id null, unlocked_at and released_by null, and no device or group links. Every row that ever held a lock has its global lock, and the database refuses a held row without one, so global_lock_id IS NULL reads as “retired without ever being held”. From then on the reference and owner answer like any retired one: getAndLockResources is refused with RETIRED, and unlockResources answers code: RETIRED with releasedBy: null.

    So a retire no longer needs to wait until every lock request of the reference has been answered. A lock request and a retire of the same reference and owner take turns, also before the reference has a row. A request that commits first leaves a held lock, which the retire refuses with LOCK_HELD: unlock it, then retire again. A request that comes after the retire is refused with RETIRED. Lock requests of the same reference and owner also take turns with each other, which changes nothing in what they answer.

    Newest row retireLock answers Changes
    held success: false, lockExists: true, code: LOCK_HELD nothing
    released, not retired success: true, lockExists: true, alreadyRetired: false, message: "Lock retired" marks it retired
    retired, once held success: true, lockExists: true, alreadyRetired: true, message: "Lock already retired" nothing
    none success: true, lockExists: false, alreadyRetired: false, message: "No lock was taken; retired, so none can be taken until its history is pruned" records the reference retired: inserts the retired row that never held anything
    retired, never held success: true, lockExists: false, alreadyRetired: true, message: "Lock already retired" nothing

    A retire holds until prune_lock_history deletes the reference’s lock rows, at least one day after the retire; the reference then answers like one that never had a lock, lockState answers NONE, and a new lock request is granted. The messages and descriptions now say so instead of “never”: a retire with no lock answers “No lock was taken; retired, so none can be taken until its history is pruned”, and an unlock of a retired lock “Lock retired: nothing is unlocked or written until its history is pruned” (it was “Lock retired: its owner never unlocks it again”), and a lock request refused with RETIRED “Lock ‘…’ was retired by its owner (lock id N); it is not locked again until prune_lock_history deletes …”, which names the retired row (it was “…; it is never locked again”). The flags and codes are unchanged.

    prune_lock_history deletes a reference retired without ever being held like any retired one. It now leaves alone every reference and owner that still has a held row, whatever its newest row (see the rolling upgrade above).

    Asking for a lock’s state: lockState

    The new query lockState(reference) answers from the newest lock row for that reference and the caller, and changes nothing. It writes nothing, takes no lock that a lock request, unlock or retire would wait on, and runs no expiry sweep. It needs the same permission as unlockResources (workflow-execution:write) and refuses a caller without it with the same error codes. Another owner’s lock with the same reference answers NONE.

    Newest row state releasedBy unlockedAt retiredAt expiresAt
    none NONE null null null null
    held HELD null null null its expiry, or null
    released, not retired RELEASED as unlockResources reports it: OWNER_UNLOCK, ADMIN, EXPIRY_SWEEP or CLEAR_ALL set null as it was
    retired, once held RETIRED as above set set as it was
    retired, never held RETIRED null null set null

    A lock past its expiry that no expiry sweep has released yet answers HELD, with its expiresAt in the past. The next lock request of any owner runs the sweep, so such a lock can be released at any moment.

    Before 2.7.0 a release deleted the row. A release by clear_lock or the admin action that failed between marking the row and deleting it left a row with locked = false and neither unlocked_at nor released_by. Since 2.7.0 such a row is kept. If one exists, it now reads as released with an unknown cause: lockState answers RELEASED with releasedBy: null, and unlockResources answers Lock not found with releasedBy: null, as releases before 2.7.0 did. 2.7.0 read such a row as released by its owner’s unlock and answered success: true, alreadyReleased: true, releasedBy: OWNER_UNLOCK. That told the workflow engine that the run’s writes had been applied when they never were. This release corrects it.

    Which lock an answer is about: lockId

    HELD alone does not say which lock is held. The workflow engine’s lock request can time out on its side while it is still queued in core. The engine retries, is granted, and works under that lock. If an admin then releases it, the first request can still land and be granted a new lock of the same reference. lockState answers HELD for both, so the engine could not tell that its lock had ended and another run could have changed the devices in between.

    Every answer about a lock now names the lock row it is about by the row’s id:

    Answer Field Names
    getAndLockResources lock.id (served before; now a documented contract) the new row, or with lockAlreadyExisted: true the row that already holds the lock; lock is null on a refusal
    lockState lockId: ID, new the newest row; null exactly when state is NONE
    unlockResources lockId: ID, new the newest row the unlock read: the row it released, the row a refusal left held, or the row released or retired before; null when there is no row, and on an UNEXPECTED refusal that failed before reading it
    retireLock lockId: ID, new the row retired now or before, the held row LOCK_HELD refused, or the row that records a reference retired without ever being held

    One id is one continuous hold. A lock released and taken again, by anyone and for any reason, is a new row with a new id, so an engine that keeps the lock.id it was granted and reads a different lockId knows its lock ended, also when the state is HELD. The id is the row’s primary key, the same number the admin shows. Ids come from the database’s id sequence, which no delete rewinds, so a row prune_lock_history deleted never has its id given to a new row. Restoring core’s database from an older backup, resetting that sequence by hand, or moving the database without its sequence values is outside this guarantee. Logical replication, as used for a blue/green or major-version move, does not carry sequence values: sync the sequence of core_compositelock before the new primary takes lock requests. Physical replicas and crash recovery keep it.

    ID is a string on the wire, for example "4711". The generated TypeScript clients type it as number; compare it as a string.

    An auditor finds a lock by its id in the admin: the Composite locks list has an ID column, and its search matches an exact id as well as owners, references and actor usernames that contain it. Core’s log lines about a lock name it as lock id N: a grant, a repeated grant of a held lock, every answer to an unlock (released, refused, already released, not found with how the lock was released, retired, and LOCK_REPLACED, which names the newest row and the named one), every retire answer, and every release without its owner: by the admin action, by the expiry sweep (“Expiry sweep released lock …: lock id N”, which replaces “Releasing expired lock CompositeLock (N, Held)”) and by clear_lock (one “clear_all released lock …: lock id N” line per lock). A release line is logged only once its release committed, so a sweep or an admin action that rolls back logs none. An unlock that finds no row at all logs “lock not found” without an id. A retire refused with LOCK_HELD is now a warning, a repeated retire is logged too, and a retire of a reference with no lock reads “Retired … without it ever being held”.

    Unlocking only the lock you hold: the lockId argument

    An id in the unlock answer comes too late for the case above. The engine’s last unlock carries the run’s writes. If it lands on the late lock B, core applies those writes under B before the engine can see B’s id, and another run may have changed the devices in between. So unlockResources takes an optional argument lockId: ID, the lock.id the caller was granted. With it, core writes and releases only when that lock is the caller’s newest lock of the reference. Otherwise it writes nothing, releases nothing, and answers the new code LOCK_REPLACED. Core compares the two inside the same transaction, under the same per-reference turn and row lock as every unlock, so a late grant that commits while the unlock waits is seen. Without the argument, an unlock answers exactly as before. Core’s own lock blocks (with_lock, with_try_lock, wait_for_lock; no request path of this release uses them) now release by the id they were granted: when an admin released a block’s lock and the same owner and reference were granted again meanwhile, leaving the block no longer releases that newer lock.

    “Named” is the lock the argument names; “newest” is the caller’s newest lock row of the reference. A named id that is not one of the caller’s lock rows of this reference reads exactly like an id that does not exist: it does not exist, it was pruned, it belongs to another owner or another reference, or it is not spelled as core serves ids. Core reads an id only in the spelling it serves: ASCII digits without a leading zero, or an integer of that value. "04711", "+4711" or digits of another script name no lock, in the guard and in lockState alike. Nothing about another owner’s lock is answered.

    Case success lockExists releasedBy unlockedAt lockId code Writes
    no lock row at all false false null null null null (“Lock not found”) none
    named is the newest as without the argument null the named as without the argument as without the argument
    named is not the newest, newest held false true how the named lock ended when it was released the newest LOCK_REPLACED none; the newest stays held
    named is not the newest, newest released or retired false false how the named lock ended when it was released the newest LOCK_REPLACED none
    named is not one of the caller’s, a newest row exists false whether the newest is held null null the newest LOCK_REPLACED none; the newest is unchanged
    named is the caller’s and still held, a newer retired row exists (only the rolling-upgrade leftover above) false false null null the newest LOCK_REPLACED none; the named lock stays held

    On LOCK_REPLACED, lockId and lockExists describe the newest row, while releasedBy and the new field unlockedAt describe the named lock. unlockedAt is null on every other answer. LOCK_REPLACED wins over RETIRED when the named lock is not the newest: the answer is about the lock the caller named, and nothing is written either way. Retrying does not help, because the named lock never becomes the newest again.

    LOCK_REPLACED with releasedBy: OWNER_UNLOCK says the caller’s writes did land. The named lock was released by its own owner’s earlier unlock, which applied that unlock’s dbUpdates; without the newer row the same call would have answered alreadyReleased: true. This is what an engine sees when the answer to its unlock was lost, a late grant of the same reference landed, and it retried the unlock: this call writes nothing, and the writes of the first are in. With lockExists: true the newest row is then another hold of the caller’s for this reference, the late grant. Nothing releases it on its own, and a lock the workflow engine takes has no expiry: it stays held until it is unlocked by its id or released by an admin. With releasedBy ADMIN, EXPIRY_SWEEP or CLEAR_ALL, the named lock was released without its owner and its writes were never applied. With releasedBy null, core has no record of how the named lock ended: the id is not one of the caller’s locks of this reference (it never was, or it was pruned), its release predates 2.7.0 and left no cause, or it is still held under a newer retired row (the rolling-upgrade leftover). Core then cannot say whether its writes were applied.

    Never send dbUpdates with the lockId of a LOCK_REPLACED answer. That id names the lock taken after the caller’s, and naming it passes the guard and applies the writes under that lock, which is exactly what the guard prevents. Name only the id the caller’s own grant answered.

    lockState takes the same optional lockId and then answers for that row instead of the newest, so a caller can learn how its lock ended when a newer one exists. An id that is not one of the caller’s lock rows of this reference answers NONE.

    What a lock row is, in the admin

    The admin’s Composite locks list has a State column and a State filter. The change page shows the same state. The states are: Held; Released by the owner unlock, by an admin, by the expiry sweep or by clear_lock; Released, cause unknown; Retired; and Retired without ever being held. “Expires in” shows - on a row that is not held; it used to say “until unlocked” or “expired”. The “expired” column is false on a row that is not held, so a lock released by its owner and since past its expiry no longer reads as released by the expiry sweep. A row’s name carries its state, for example CompositeLock (12, Retired without ever being held) instead of CompositeLock (12, Locked: False).

    The admin no longer adds lock rows or their device and group links: the add buttons are gone and the add pages answer 403. They could already not be changed or deleted there. Lock rows are written only by lock requests, unlocks and retires, and deleted only by prune_lock_history.

    The Composite locks list’s search matches an exact id, ORed with a partial match on owner, reference and actor username: searching 12 lists lock 12 and every lock whose owner, reference or actor username contains “12”.

    Workflow engine

    The operation in neops-graphql/graphql/lock_state.graphql selects every field of lockState, and the operations for unlockResources and retireLock select lockId. lock_state.graphql and unlock_resources.graphql pass the optional lockId argument, and unlock_resources.graphql selects unlockedAt; get_and_lock.graphql already selected lock.id. An engine built against 2.7.0 or 2.8.0-beta.1 does not select lockId and reads every answer as before. Deploy an engine that sends or selects lockId only after every core pod runs this release: a 2.7.0 or 2.8.0-beta.1 pod answers such a call with a GraphQL validation error. Such an engine must not fall back to an unguarded unlock on that error; the unlock was not executed, so it retries once the rollout is done. An engine built against 2.7.0 reads every retireLock answer it knew the same way: a retire with no lock still answers success: true, lockExists: false, alreadyRetired: false, with a new message. Only a repeated retire of a reference retired without a lock is new: lockExists: false with alreadyRetired: true.

    Going back

    lockId and the lockId arguments need no migration. An engine that relies on them cannot run against a core older than this release, 2.8.0-beta.1 included: the fields and arguments do not exist there, and the operation fails with a GraphQL validation error. Roll the engine back before core.

    2.8.0-beta.1 runs with both migrations in place: it writes a row without a global lock only in the shape 0211 requires, apart from its admin add form. 2.7.0 runs with 0210_composite_lock_never_held and 0211_composite_lock_never_held_is_retired in place: it always gives a lock its global lock, and it reads a reference retired without ever being held as retired, as described in the upgrade notes above.

    migrate core 0209_lock_history makes global_lock_id required again. It fails while a retired row that never held anything is kept. Delete those rows first. This forgets that their references were retired, so their owner can lock them again:

    DELETE FROM core_compositelock WHERE global_lock_id IS NULL;

    Going back below 2.7.0 migrates below 0209_lock_history, so it passes through this step, and no such row is left for the earlier release.
