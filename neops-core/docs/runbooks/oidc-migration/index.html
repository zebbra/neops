    OIDC Migration Runbook

    Swap the neops auth plugin neops_auth_keycloak → neops_auth_allauth, then — only if Keycloak runs inside this compose stack — upgrade Keycloak 16.1.1 → 26.1. Docker-compose deployments only.

    At a glance

    Phase You do Time Undo
    Pre-flight Snapshot + scan for bad rows ~10 min —
    Part 1 — everyone Flip the plugin, verify the bridge ~20 min R1
    Part 2 — KC-in-stack only Keycloak 16 → 26 ~20–35 min R2
    Rollback (if needed) Reverse order: R2 → R1 ~10–15 min — 
            PART 1 (everyone)                 PART 2 (KC in this stack only)
   ┌───────────────────────────┐     ┌────────────────────────────────────┐
   │ snapshot → scan → flip →  │     │ dump → edit compose → restore →     │
   │ start → verify bridge      │ ──► │ start KC 26 → verify                 │
   └───────────────────────────┘     └────────────────────────────────────┘
                 │                                     │
                 └──────────────► ✗ anything fails ◄───┘
                                        ▼
                              ┌──────────────────────┐
                              │  ROLLBACK   R2 → R1   │
                              └──────────────────────┘

    Pick your path:

    Your deployment Do Then
    Default fleet (neops_auth_django, no Keycloak) ⛔ Wrong doc — you’re not migrating OIDC. See the release-wide breaking changes in Reference.
    Externally-managed Keycloak (KC not in this stack) Part 1 only → Cleanup
    Keycloak runs in this compose stack Part 1 + Part 2 → Cleanup

    🛑 The one rule. Two services are named postgres — one under neops/, one under keycloak/. Dropping the wrong one is the only unrecoverable mistake here; every destructive block below therefore opens with a cd + pwd guard.

    ⚠️ HEADS-UP — one terminal per Part. Each Part’s opening header (cd, pwd, and for Part 2 . .env) sets context the sub-steps inherit. If you take a break and resume in a fresh shell, re-run that header first.

    How to read this

    Five signposts, used consistently:

    Means
    🛑 GATE Stop and resolve before continuing. Each GATE says what to do on a “no” — usually fix in place and retry; only where it says abort to Rollback do you roll back. (Rollback is only ever reached from a GATE, never from the markers below.)
    ⚠️ HEADS-UP A non-fatal gotcha. Read it before you run the block.
    ✅ Success looks like The step’s pass bar — compare your output against it before judging the GATE that follows.
    ✅ EXPECTED Looks alarming, is normal. Don’t panic.
    💡 WHY One line of rationale, so you trust the step.

    Before you start

    Tick every box. The 🛑 boxes are hard gates — a “no” means the flip will fail or boot an insecure/broken backend.

    Auth backend config (all new; allauth needs these — the defaults are dev-only):

    • 🛑 RSA JWT keys generated and mounted into the backend service. Once allauth is loaded, daphne/uvicorn/gunicorn will not boot without them (signing moved HS256 → RS256).
    • Generate once: make generate-jwt-keys → writes backend/secrets/neops-jwt-{private,public}.pem.
    • Add the mount + NEOPS_JWT_PRIVATE_KEY_PATH / NEOPS_JWT_PUBLIC_KEY_PATH to the backend service (shape: docker/docker-compose.enterprise-oidc.yml). This is step 1.4 — don’t skip it or up -d backend crash-loops mid-window.
    • Multi-replica: generate once, mount the same pair to every replica. Per-container keys → tokens signed by one replica are rejected by another.
    • 🛑 NEOPS_FRONTEND_CALLBACK_URL(S) and NEOPS_FRONTEND_LOGIN_URL set to your real frontend origin. They default to http://localhost:4242/...; unset in prod, every OIDC login and logout redirect dead-ends at localhost.
    • 🛑 NEOPS_PUBLIC_URL set + DJANGO_ALLOWED_HOSTS tightened to your real hostname(s). appSettings is unauthenticated and derives the login URL from the request Host when NEOPS_PUBLIC_URL is empty; with the image default DJANGO_ALLOWED_HOSTS=*, that URL is attacker-controllable (login-URL phishing / cache-poisoning). Mandatory for allauth. (The app logs a neops_auth_allauth.W003 boot warning until NEOPS_PUBLIC_URL is set.)
    • 🛑 RATELIMIT_IP_META_KEY set if a proxy/gateway terminates the client connection (neops-gql-gtw, neops-secure-gateway, traefik). Set it to the META key of a header your ingress fills with the real client IP and strips from inbound requests (e.g. HTTP_X_REAL_IP). Otherwise the post-flip re-login wave collapses into one shared refreshToken bucket → 429 → fleet mass-logout. Never point it at a spoofable client-settable header.
    • 🛑 Redis is wired to the Django cache (REDIS_URL set). With any rate limit active (default NEOPS_OIDC_RATE_LIMIT=20/m), the allauth app refuses to boot unless CACHES.default is a shared backend (neops_auth_allauth.E002) — which it only is when REDIS_URL is set. (The sibling check E001 covers a missing django_ratelimit package, which the shipped image already includes.)

    Keycloak client config (on your existing realm, before the flip — works on any KC version, including 16):

    • 🛑 The allauth login redirect URI is registered on the neops client. The new flow uses the authorization-code redirect; the legacy plugin used password grants only, so a production client typically has no usable redirect URI. Register your literal https://<NEOPS_PUBLIC_URL host>/accounts/oidc/<realm-name>/login/callback/ under Clients → your neops client → Valid Redirect URIs. Missing → the very first login dies on Keycloak’s “Invalid parameter: redirect_uri” page.
    • 🛑 On Keycloak ≤ 17: your NEOPS_FRONTEND_LOGIN_URL is ALSO in Valid Redirect URIs. Old Keycloak has no separate post-logout allowlist — it validates the logout redirect against this same list. Without the entry, every logout dies on a 400 “Invalid redirect uri” page with the SSO session still alive (verified live against KC 16). On KC ≥ 18 the equivalent lives in Valid post logout redirect URIs (registered in 2.6 for the in-stack upgrade path).
    • 🛑 The client-roles mapper emits resource_access into the ID token (or userinfo). Keycloak’s stock mapper is access-token-only and the backend never stores IdP access tokens — with the default, role sync silently no-ops: users keep their bridged roles forever, KC role changes stop propagating, and each login logs a “no resource_access claim” warning. Enable Add to ID token on the client-roles mapper, then confirm via Clients → your neops client → Client scopes → Evaluate that resource_access.<client_id>.roles appears in the ID token. Details: docs/oidc-authentication.md.

    Safety net & rehearsal:

    • 🛑 App DB snapshot taken and restore-verified — see 1.1. pg_restore --list alone is not enough. This is your only rollback path for neops_auth_django and for app-DB corruption.
    • Legacy and new neops-core image tags recorded.
    • Forward and rollback drilled on staging in the last 7 days — against both make oidc-scenario-flip and make oidc-scenario-flip-start.
    • This runbook’s Forward and Rollback sections read end-to-end.

    Frontend compatibility:

    ⚠️ HEADS-UP: upgrade frontends FIRST, backend second. New frontends degrade gracefully on the old backend; old frontends break on the new one.

    Your frontend after the flip Result
    New (consumes appSettings.oidcProviders) ✅ OIDC SSO works
    Legacy in-browser flow ❌ No OIDC — and no local-login fallback

    Bottom line: allauth hard-disables local login (NEOPS_LOCAL_LOGIN_ENABLED=False, no env override). Any frontend still on the legacy flow loses all ability to log in the moment you flip. Upgrade it first — concretely, before 1.3:

    # deployments/docker-compose/neops/.env — bump the frontend image tag(s):
#   NEOPS_WEBCLIENT_IMAGE_TAG=<OIDC-capable web-client tag>
#   NEOPS_LEGACY_FRONTEND_IMAGE_TAG=<OIDC-capable legacy-frontend tag>   # only if deployed
docker compose up -d web-client          # plus: docker compose up -d frontend, if deployed

    🛑 GATE: open the login page — the new frontend must render and local login must still work against the not-yet-flipped backend (new frontends degrade gracefully; OIDC buttons appear only after the flip). An old frontend at flip time = fleet-wide lockout.

    Part 2 extras (only if Keycloak runs in this stack) - [ ] Both KC images present locally: `jboss/keycloak:16.1.1` and `quay.io/keycloak/keycloak:26.1`. - [ ] Legacy KC postgres dir intact: `ls deployments/docker-compose/keycloak/data/keycloak_postgres/PG_VERSION`. - [ ] KC 26 env validated on staging — see [Appendix D](#appendix-d--kc-26-required-environment). - [ ] Truststore migration planned if KC 16 used `customcerts/` — see [Appendix E](#appendix-e--truststore-migration). - [ ] For KC DBs > 5 GB, raise `KC_READY_MAX_ITER`. Rule of thumb: 1 min/GB + 5 min headroom.
    Multi-IdP security precondition Every IdP must enforce `email_verified: true`, or each per-provider `trust_email_without_verification` opt-out must be documented. Without it, an attacker can register a victim's email and take over the account via email auto-linking. See [Appendix C](#appendix-c--multi-idp-safety).
    Kubernetes / Helm operators — read this A **rolling deploy across this release WILL break auth.** Migration `core/0175` is destructive and the release switches token signing, so overlapping old/new pods corrupt auth for the whole window (old pods query dropped columns; old/new pods mint mutually-unacceptable tokens). You **must** use `strategy: Recreate` (or scale the old Deployment to zero before the new one starts). The chart's default `RollingUpdate` is **unsafe here**. The docker-compose procedure below enforces this by stopping all app services before migrating. Full k8s orchestration is out of scope, but Recreate / scale-to-zero is **mandatory, not optional**.

    Part 1 — Plugin flip

    keycloak → allauth · Phase 1 of 2

    💡 Why: the neops app never stored OIDC identity in socialaccount_* before. A one-time bridge migration copies django_keycloak_* → socialaccount_* so existing users keep their identity. It reads the legacy tables; it never writes to them, which is what makes rollback cheap.

    Production loads multiple compose overlays via .env.dist’s COMPOSE_FILE. A bare docker compose … resolves the full stack.

    1.1 Snapshot the app DB

    ⏱️ ~5 min · Phase 1 of 2

    💡 Why: the only rollback path for app-DB corruption (and the mandatory one for a neops_auth_django base). Verify it restores — a dump that won’t restore is not a backup.

    cd deployments/docker-compose/neops
pwd | grep -q '/neops$' || { echo "FATAL: wrong directory"; exit 1; }

mkdir -p ./backup/pre-flip
DUMP=./backup/pre-flip/$(date -u +%Y%m%dT%H%M%SZ)-app.dump
docker compose exec -T postgres \
  pg_dump -U neops -d neops -Fc --no-owner --no-privileges > "$DUMP"
test -s "$DUMP" || { echo "FATAL: dump is empty"; exit 1; }

# Restore into a throwaway DB and compare row counts against live.
docker compose exec -T postgres psql -U neops -d postgres -c \
  "DROP DATABASE IF EXISTS pre_flip_verify; CREATE DATABASE pre_flip_verify;"
docker compose exec -T postgres pg_restore -U neops -d pre_flip_verify \
  --no-owner --no-privileges --exit-on-error < "$DUMP"

COUNTS="SELECT 'auth_user='||COUNT(*) FROM auth_user
  UNION ALL SELECT 'oidc='||COUNT(*) FROM django_keycloak_openidconnectprofile"
echo "Dump:" && docker compose exec -T postgres psql -U neops -d pre_flip_verify -tA -c "$COUNTS"
echo "Live:" && docker compose exec -T postgres psql -U neops -d neops -tA -c "$COUNTS"
docker compose exec -T postgres psql -U neops -d postgres -c "DROP DATABASE pre_flip_verify;"
echo "Dump verified: $DUMP"

    ✅ Success looks like: the Dump and Live count blocks are identical. 🛑 GATE: counts diverge → the dump is broken. Fix it before going further.

    1.2 Pre-flight scan for bad rows

    ⏱️ ~2 min · Phase 1 of 2

    💡 Why: neops_init runs migrate as one unit. A bad row makes a core migration abort mid-run — after 0175 has already destroyed refresh-token state. Surfacing these now, read-only, keeps the abort out of your maintenance window.

    All queries are read-only against the live app DB.

    echo "1) OIDC profiles pointing at a missing auth_user (aborts the bridge insert):"
docker compose exec -T postgres psql -U neops -d neops -tA -c "
  SELECT p.id, p.user_id
  FROM django_keycloak_openidconnectprofile p
  LEFT JOIN auth_user u ON u.id = p.user_id
  WHERE u.id IS NULL;"

echo "2) Realms/clients with NULL secret / client_id / server URL (NULL url aborts the bridge):"
docker compose exec -T postgres psql -U neops -d neops -tA -c "
  SELECT r.name, c.client_id, c.secret, s.url
  FROM django_keycloak_realm r
  JOIN django_keycloak_client c ON c.realm_id = r.id
  JOIN django_keycloak_server s ON s.id = r.server_id
  WHERE c.secret IS NULL OR c.client_id IS NULL OR s.url IS NULL;"

echo "3) Duplicate Role.name carrying permission grants (migration 0178 ABORTS on these):"
docker compose exec -T postgres psql -U neops -d neops -tA -c "
  WITH dup_names AS (
    SELECT name FROM core_role GROUP BY name HAVING COUNT(*) > 1
  ),
  grant_bearing AS (
    SELECT role_id FROM permissions_simple_rolepermissionelement
    UNION SELECT role_id FROM permissions_simple_roleneopstask
    UNION SELECT role_id FROM permissions_simple_roledevicegroup
    UNION SELECT role_id FROM permissions_simple_rolescope
  )
  SELECT r.name, COUNT(*) AS rows, COUNT(g.role_id) AS grant_rows
  FROM core_role r
  JOIN dup_names d ON d.name = r.name
  LEFT JOIN grant_bearing g ON g.role_id = r.id
  GROUP BY r.name
  HAVING COUNT(g.role_id) > 0;"

echo "4) Duplicate auth_user emails (advisory: ambiguous post-flip auto-link):"
docker compose exec -T postgres psql -U neops -d neops -tA -c "
  SELECT lower(email) AS email, COUNT(*)
  FROM auth_user WHERE email <> ''
  GROUP BY lower(email) HAVING COUNT(*) > 1;"

    🛑 GATE: queries 1, 2, and 3 must return zero rows. A hit aborts neops_init mid-migration. - Query 1 hits: the profile is orphaned — after confirming the user_id really has no auth_user row, DELETE FROM django_keycloak_openidconnectprofile WHERE id IN (<ids>). - Query 2 hits: escalate, don’t guess — a NULL client secret/id/server URL means the legacy realm config predates working SSO; inventing a value bridges a broken provider. - Query 3 hits: consolidate by hand (move the grants onto one role, delete the other) before flipping. - Query 4 is advisory — duplicate emails don’t break the bridge but make post-flip auto-link ambiguous (Appendix C). Resolve or note them.

    ⚠️ HEADS-UP: if permissions_simple is not installed, query 3’s grant tables don’t exist (it errors) — that’s fine: 0178 then auto-merges duplicates safely. Run only the quick check for awareness: SELECT name, COUNT(*) FROM core_role GROUP BY name HAVING COUNT(*) > 1;

    1.3 Stop the legacy app

    ⏱️ ~1 min · Phase 1 of 2

    💡 Why: stop what’s actually running (overlays differ per deployment), not a hard-coded list. postgres stays up — the rollback restore needs it.

    docker compose ps --services --status running | tee /tmp/running-services.txt
svcs=$(grep -vxE 'postgres' /tmp/running-services.txt | tr '\n' ' ')
[ -n "$svcs" ] || { echo "FATAL: no non-postgres services running — refusing to run a bare 'stop'"; exit 1; }
docker compose stop $svcs

    1.4 Flip the plugin + set required env

    ⏱️ ~3 min · Phase 1 of 2

    💡 Why: the actual flip — an env edit, no DB writes yet. Nothing here is destructive.

    Edit deployments/docker-compose/neops/.env (substitute your literal values):

      # The flip itself:
- NEOPS_PLUGINS=… neops_auth_keycloak …
+ NEOPS_PLUGINS=… neops_auth_allauth …
- NEOPS_IMAGE_TAG=<legacy>
+ NEOPS_IMAGE_TAG=<new>

  # Required allauth config (see the "Before you start" gates):
+ NEOPS_PUBLIC_URL=https://neops.customer.example
+ DJANGO_ALLOWED_HOSTS=neops.customer.example
+ NEOPS_FRONTEND_CALLBACK_URL=https://neops.customer.example/auth/callback
+ NEOPS_FRONTEND_LOGIN_URL=https://neops.customer.example/login
+ RATELIMIT_IP_META_KEY=HTTP_X_REAL_IP        # only behind a connection-terminating proxy

    And add the JWT key mount + paths to the backend service (shape in docker/docker-compose.enterprise-oidc.yml):

    # backend service:
    environment:
      NEOPS_JWT_PRIVATE_KEY_PATH: /run/secrets/neops-jwt-private.pem
      NEOPS_JWT_PUBLIC_KEY_PATH:  /run/secrets/neops-jwt-public.pem
    volumes:
      - ../../../backend/secrets/neops-jwt-private.pem:/run/secrets/neops-jwt-private.pem:ro
      - ../../../backend/secrets/neops-jwt-public.pem:/run/secrets/neops-jwt-public.pem:ro

    ⚠️ HEADS-UP: if this deployment sets AUTH_PROVIDERS_CONFIG_PATH (JSON provider seed), either unset it while relying on the bridge, or make its provider_id exactly the legacy realm name. Otherwise the seed and the bridge create two SocialApps for one IdP (duplicate login buttons). You’ll re-check this in 1.6.

    ✅ Success looks like: docker compose config resolves with no unset-variable warnings and shows neops_auth_allauth. 🛑 GATE: config errors → fix now (nothing destructive has run).

    1.5 Start the new app + confirm the bridge ran

    ⏱️ ~5 min · Phase 1 of 2

    docker compose up -d neops_init          # runs migrations, incl. the bridge

if ! docker compose wait neops_init; then
  echo "FATAL: neops_init exited non-zero — 'docker compose logs neops_init'"
  exit 1
fi

    Confirm the bridge recorded itself (authoritative — the log stream won’t show per-row skips; 1.6’s count match is how you catch those):

    if ! docker compose run --rm --no-deps -T backend python manage.py shell -c "
from django.db import connection
with connection.cursor() as c:
    c.execute(\"SELECT 1 FROM django_migrations WHERE app='neops_auth_allauth' AND name='0003_bridge_legacy_keycloak'\")
    assert c.fetchone(), 'bridge migration row missing'
print('OK bridge migration recorded')
"; then
  echo "FATAL: bridge migration not recorded — inspect neops_init"
  exit 1
fi

    💡 WHY run --rm --no-deps: backend isn’t started yet and we want to verify before serving traffic. --no-deps avoids starting redis; migrate/shell aren’t server processes, so the JWT-key boot gate doesn’t apply to them (it will apply to backend below — that’s why the keys had to be wired in 1.4).

    Start the app. Restart what was running pre-flip (from 1.3’s capture), e.g.:

    docker compose up -d backend worker beat $(grep -vxE 'postgres|neops_init' /tmp/running-services.txt | tr '\n' ' ')

    🛑 GATE: - backend crash-loops (docker compose logs backend — almost always missing/mis-mounted JWT keys) → fix in place: wire the key mount per 1.4, then docker compose up -d backend and re-check. Nothing destructive has happened; no rollback needed. - neops_init failed or the bridge row is missing → the migration itself didn’t complete → abort to Rollback.

    1.6 Validate

    ⏱️ ~5 min · Phase 1 of 2

    Bridge row-count match — the authoritative skip detector. Excludes service accounts (the bridge skips them by design):

    docker compose exec -T backend python manage.py shell -c "
from allauth.socialaccount.models import SocialAccount, SocialApp
from django.db import connection
app = SocialApp.objects.filter(provider='openid_connect').first()
if app is None:
    print('FATAL: no SocialApp(provider=openid_connect) — bridge did not run'); raise SystemExit(1)
realm = app.provider_id
sa = SocialAccount.objects.filter(provider=realm).count()
with connection.cursor() as c:
    c.execute('''SELECT COUNT(*) FROM django_keycloak_openidconnectprofile p
                 JOIN auth_user u ON p.user_id = u.id
                 WHERE u.username NOT LIKE 'service-account-%' ''')
    legacy = c.fetchone()[0]
print(f'realm={realm!r} legacy={legacy} bridge={sa}')
print('MATCH' if legacy == sa else f'MISMATCH: {sa} bridged for {legacy} legacy profiles')
dups = SocialApp.objects.filter(provider='openid_connect').count()
print(f'SocialApp count={dups}' + (' — WARN: duplicate provider seed?' if dups > 1 else ''))
"

    ⚠️ HEADS-UP — multi-realm DBs always “MISMATCH” here. The check compares all legacy profiles against one realm (SocialApp…first()), and its SocialApp count > 1 line will mislabel a legitimately multi-realm customer as “duplicate seed”. Count per realm instead, and confirm against the per-row bridge logs before rolling back on this check alone.

    ⚠️ HEADS-UP — the service-account-% filter is a heuristic. On a very old legacy DB (pre django-keycloak migration 0004) the bridge migrates all profiles, and a human user literally named service-account-* skews the count. Same rule: per-row bridge logs are the authority, not this aggregate.

    KC URL check — confirm allauth points at the running KC, with the path layout that KC actually serves.     Release-wide breaking changes (default fleet)

    💡 These affect every deployment upgrading the image — including the default neops_auth_django fleet not doing this Keycloak migration. They belong in the release notes, not only here.

    1. RSA JWT keys now required for neops_auth_django and neops_auth_allauth. Signing moved HS256 (SECRET_KEY) → RS256 (PEM pair). A server process won’t boot without them — see the first Before-you-start gate. neops_auth_keycloak and neops_auth_static_api_key are exempt (boot check skipped).
    2. All users re-authenticate once. core/0175_refreshtoken_rotation_revocation runs DELETE FROM django_refreshtoken (plaintext tokens can’t be re-hashed). For neops_auth_django, the HS256→RS256 switch also invalidates existing access tokens. Schedule the window; tell users.
    3. Image-only rollback is unsafe for neops_auth_django. core/0175 is forward-only: it deletes every refresh-token row and its reverse is a DB no-op. It’s a SeparateDatabaseAndState, so migrate core 0174 reverts Django’s model state while the DB is untouched — leaving the ORM believing in a schema the DB lacks. Rolling back needs the pre-upgrade DB snapshot. Keycloak → allauth is unaffected — it uses oidc_profile.refresh_token, not django_refreshtoken; the rollback in this runbook is safe.
    4. Don’t switch auth plugins on a live DB. core/0175’s dependency on neops_auth_django’s 0005 resolves per installed plugin at import time; a DB first migrated under one plugin set can raise InconsistentMigrationHistory under a different set. The Part-1 flip here (keycloak → allauth) is safe; arbitrary swaps are not — use a fresh DB or migrate --fake the node deliberately.

    Appendix A — Docker compose pre-2.20

    docker compose wait needs 2.20+. Older compose — replace the 1.5 wait with a poll:

    for i in $(seq 1 60); do
  ec=$(docker compose ps -a --format '{{.ExitCode}}' neops_init 2>/dev/null | head -1)
  [ -n "$ec" ] && [ "$ec" != "0" ] && { echo "FATAL: neops_init exited $ec"; exit 1; }
  [ "$ec" = "0" ] && break
  sleep 2; [ "$i" -lt 60 ] || { echo "FATAL: neops_init never exited"; exit 1; }
done

    Appendix B — Secure-delete on macOS

    shred isn’t on macOS or slim Linux images. The rm -f fallback removes the directory entry but doesn’t overwrite blocks. On macOS with TRIM SSDs that’s effectively secure for short-lived /tmp files. On a multi-tenant host or HDD, install srm (brew install coreutils) and use srm -m -z.

    Appendix C — Multi-IdP safety

    allauth auto-links by email (SOCIALACCOUNT_EMAIL_AUTHENTICATION=True + SOCIALACCOUNT_AUTO_SIGNUP=True). A second IdP without strict email_verified lets an attacker register a victim’s email and take over the account. The _enforce_email_verified adapter gate defends the default IdP; per-provider trust_email_without_verification opt-outs bypass it. Document any opt-out before flipping; treat the adapter setting as load-bearing.

    Appendix D — KC 26 required environment

    KC 26 can’t use start-dev in production. Minimum env for start (the validated scenario compose additionally sets KC_BOOTSTRAP_ADMIN_USERNAME/_PASSWORD — a no-op on a restored DB, which already has its admin — and KC_HOSTNAME_BACKCHANNEL_DYNAMIC for its split internal/external hostname setup; neither is required for a standard single-hostname deployment):

    Variable Purpose
    KC_DB DB vendor (postgres)
    KC_DB_URL / KC_DB_USERNAME / KC_DB_PASSWORD DB connection
    KC_HOSTNAME Public hostname KC serves on
    KC_HOSTNAME_STRICT true with real TLS; false only behind a TLS-terminating proxy
    KC_PROXY_HEADERS xforwarded behind traefik or equivalent
    KC_HTTP_ENABLED true if a TLS-terminating proxy talks HTTP to KC
    KC_HEALTH_ENABLED true — required for the 2.5 / R2 health probes

    Validated set: docker/oidc-test-scenario/compose.oidc.start.yml.

    Appendix E — Truststore migration

    KC 16’s customcerts/ / customca.jks / truststore.cli mounts do not carry into KC 26. The unified KC 25+ mechanism for outbound TLS (LDAP, OIDC brokering, SMTP, custom HTTPS):

    KC_TRUSTSTORE_PATHS=/opt/keycloak/conf/truststores/customca.jks

    Accepts a comma-separated list of files or a directory of .pem/.jks. PEM directories work natively — no JKS conversion. KC_HTTPS_TRUSTSTORE_* is deprecated (KC 25) for outbound TLS; it survives only for inbound client-cert (mTLS) validation — if you don’t know you need that, you don’t. Reference: https://www.keycloak.org/server/keycloak-truststore.

    Appendix F — Non-interactive automation

    The R2 pre-flight uses read -p "… [y/N]". Driving this from a script: comment out the read line and verify the diff out-of-band before invoking.
