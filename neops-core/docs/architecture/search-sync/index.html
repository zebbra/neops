    Search index sync

    How Neops Core keeps Elasticsearch in step with PostgreSQL, which guarantees that sync gives, and which test proves each one. This page owns writes, sync state and repair. Index layout and query routing (LuceneToESParser, FIELD_CONFIG, ES|QL chains) are in backend/neops_modules/opencore/neops_core/neops/core/documents/ELASTICSEARCH.md; the operator view and the runbook are in the release notes. The design comes from https://github.com/zebbra/neops-core/pull/2184 and https://github.com/zebbra/neops-core/pull/2379, refined by the pull requests merged on top of the latter (https://github.com/zebbra/neops-core/pull/2402 to https://github.com/zebbra/neops-core/pull/2417).

    Read it before you change an indexed model, a document class, a GraphQL mutation that writes indexed rows, any bulk update() or QuerySet.delete() on an indexed model, the permission filter, or the commands elastic_index, sync_lookup_indices, resync_unsynced_rows and index_sync_status.

    Sync state on each row

    Every indexed model inherits ElasticSyncableModel:

    Column Meaning
    elastic_version Raised by every save except one whose update_fields all lie outside the index (no-op saves included), by every mark, by the group bump, and by moved past (see Versions). Documents and lookup rows are written with it as their external version.
    elastic_sync_status synced, pending, error, rejected, see the state machine. rejected is set by the sweep and by a rebuild; persist_sync_state stamps only synced and error.
    elastic_permission_pending A change to what grants access to the row has not reached the index yet (archiving or restoring a device, interface or client counts as one). Restricted users do not see the row through the index while it is set. A save of a flagged row sets pending, so the flag never travels alone; the sweep takes flagged rows in every status but rejected, synced included: no write leaves a flagged row synced now, but an untagged build of the ES
    elastic_status_changed_at When the status or the version last changed: set by every save that raises the version, every mark, every stamp and every status write of the sweep. The sweep’s grace is measured on it. A row already in error keeps it when it fails again, so a row that keeps failing still ages.
    elastic_sync_retry_at When a write of the row last failed (error_stamp), or the end of the lease a sweep run holds on the row (ROW_LEASE_SECONDS, 30 s ahead). The sweep waits the grace after it, so other runs skip a leased row, and a run that dies leaves its rows to the next one.
    elastic_sync_hash, elastic_relation_hash Change detection. The main hash covers the row’s own columns (facts and checks through their sync schema); the relation hash covers the device’s groups, the group’s devices, the interface’s device and clients, the client’s interface and groups. A save of a synced row that changes neither does not write, unless the row is flagged. A Location’s facts and checks go through the device_group schemas (entity_type_of).

    PendingGroupIndex (group_id, created_at, no foreign key) records a committed Device.groups change whose group documents may not be written yet. The sweep leases a record by moving created_at 30 s ahead; a write that failed for the group’s own reason or was left sets it to now, and after an outage the record keeps the lease end, so created_at says when the record is next due, not when the change was made.

    A Location’s sync columns are its DeviceGroup row’s, in core_devicegroup. Every version-checked stamp, set-aside and move past is one UPDATE that compares the version on that table (sync_columns_model); an update through Location’s own manager would select the ids first and update without the version.

    The rows the sweep may take are RESYNC_CANDIDATES (elastic_syncable.py). A partial index on each table (core_device_resync_sel, core_iface_resync_sel, core_client_resync_sel, core_group_resync_sel, migration 0201_resync_selection_indexes) has that condition and the sweep’s order (resync_order), and the sweep and index_sync_status select with the same rows_to_resync, so the three cannot drift.

    A save whose update_fields all lie in fields_outside_the_index (the sync columns and the lock state) neither marks nor writes, so a lock or unlock never depends on Elasticsearch being writable. A full save() that changes only lock state still marks and writes.

    Configuration that changes the path

    • ELASTICSEARCH_DSL_AUTOSYNC (default on, off in backend/neopsapp/settings_test/base.py): when off, the signal handlers (the membership mark, the queryset soft-delete mark and a restore’s parent mark among them) and the count refresh of live rows return early, so a change writes nothing. Saves and the client recompute still mark rows (a Device.groups change and a queryset soft delete or undelete mark no device or group, so the sweep never repairs those), and the sweep, unlock recovery and execution writes (UpdateType.MANUAL) still write: main documents, lookup rows, due groups, the deletes of archived rows and their parents, and in the sweep the count parents a repaired row names itself.
    • ELASTICSEARCH_DSL_SIGNAL_PROCESSOR: web processes use NeopsSignalProcessor. The Celery worker (chart/neops-core/templates/worker.yaml, cms-worker in neops-docker-compose) uses NeopsCacheSignalProcessor: a save outside a transaction is queued by registry.add_to_cache and written by registry.flush_cache(), which picks rows by hash change only (a pending row whose hashes did not move is left to the sweep), runs outside any IndexWriteBatch and stops at its first failure, leaving the rest pending for the sweep. A change inside a transaction is written after the commit through index_committed, whatever the processor.
    • NEOPS_ELASTIC_CHANGE_DETECTION (default on): when off, every save writes, whatever the hashes say.

    Where each mark comes from:

    Change Marks inside the transaction Written after the commit
    save() of an existing row (ElasticSyncableModel.save) elastic_version + 1; pending, whatever the status was, when a field or the hash changed or the row ends flagged; the permission flag when a _PERMISSION_FIELDS column changed (deleted_at on devices, interfaces and clients; Interface.device_id; Client.interface_id, Client.location_id) or a saved client’s permission groups changed the row’s documents and lookup rows, and the parents whose counts it moved
    Device.groups add, remove, clear (registry.mark_membership_pending) each device: version + 1, pending, permission flag; one PendingGroupIndex row per group; the group row is not touched the devices in one bulk request, their lookup rows in one request per lookup index; then each group: raise the group’s version, read its members, write
    Client permission groups change (recompute_permission_groups, after a device’s groups change or an interface moves) changed clients only, locked in key order: version + 1, pending, permission flag; it notes which were synced those clients’ documents in one bulk request. A client still at the noted version, with its stored hash unchanged, keeps its lookup rows (lookups_current): they hold its location and interface, not its groups. The others’ lookup rows go in one bulk request per lookup index; a failed lookup row leaves the client error
    New row pending, version 1 (a client saves twice and starts at 2) its documents, its parents’ counts
    Soft delete of an instance (instance.delete()) a save of deleted_at, so pending, and for a device, interface or client the permission flag registry.reindex_committed_row: refresh the parents’ counts, delete the documents, then the lookup rows. The archived row is stamped synced, flag cleared, only once its own lookup rows are deleted too (_stamp_deleted); otherwise it stays error and hidden. A partner whose lookup row was not rewritten is marked pending, not hidden. Outside index_after_commit() (an unlock or an inventory mutation) a failure is only logged: the delete stands and the row waits, hidden, for the sweep
    Undelete of an instance (instance.undelete()) a save of deleted_at, so pending and, for a device, interface or client, the permission flag; its count parents (a group’s members, a device’s groups) pending, not hidden (mark_count_parents_pending, from pre_undelete) the row and its partners’ lookup rows, then its count parents as rows, each stamped at its version; a parent whose write fails is left to the sweep
    Hard delete none; the parents whose documents include the row are read before the delete (registry.count_parents_of) an instance hard_delete() deletes the documents and lookup rows twice: on pre_hard_delete, which outside a transaction runs at once, before the rows are deleted, and on post_delete, after the commit. After the commit it rewrites those parents (registry.refresh_parents) before that second delete; clients are missed. If the document delete, the row’s own lookup deletes or the parent rewrite fail, nothing is left for the sweep; a partner whose lookup row was not rewritten is marked pending for it. See limitations
    QuerySet.delete() / undelete() (SoftDeletableQS) one UPDATE deleted_at by pk, then the post_bulk_soft_delete / post_bulk_undelete signal marks every row the queryset selected (registry.mark_rows_pending, rows locked in key order): version + 1, pending, permission flag. An undelete also marks the restored rows’ count parents pending, not hidden each row through registry.reindex_committed_row: an archived row has its documents and lookup rows deleted and its parents refreshed (each parent once per commit), stamped as for an instance delete; an undeleted row is written as restored, and its count parents are written as rows, each stamped at its version; a row whose write fails is left for the sweep and the others still go. It cascades like an instance delete: a device’s interfaces are archived with it (their neighbors cleared), an interface’s discovered clients (fromimport=False) too, and an undelete restores them as an instance undelete does

    Rules the write path depends on:

    • Every signal-driven write goes through _index. Inside a transaction it registers an on_commit(robust=True) hook. Outside one the change is already committed and the write runs at once. Inside index_after_commit() (an unlock, or a GraphQL mutation under @commits_before_indexing) the hook is also recorded on the UnlockIndexWork, see Unlocks. There, once one hook failed, the later hooks of that commit write nothing, and their rows stay marked for the sweep.
    • The hook reads the committed row (registry.index_committed), never the instance in memory: a later transaction may have changed it. A row that is pending, error or rejected is written whatever its hashes say.
    • A save never clears a mark the database holds. It writes elastic_sync_status and elastic_permission_pending as F() unless it sets them itself, so a later save in the same transaction, or a concurrent save that read the row before a membership mark committed, cannot write synced over it.
    • One commit, one outage. The writes one transaction queued share an IndexWriteBatch. After the first connection error or timeout the rest fail at once with SkippedWhileUnavailable and leave their rows for the sweep. Outside a transaction the execution mutations (@fails_fast_on_index_writes), the stuck-execution cleanup and each sweep run share one batch the same way. A lookup index whose mode check failed is skipped by this process for ENSURE_FAILURE_SECONDS (10 s).
    • A parent is rewritten once per commit for its counts: the first refresh runs after the commit and already counts every change of that commit.
    • A partner’s lookup row is handed to the sweep. When a delete, archive or restore rewrites its partners’ lookup rows (a group’s member rows, a device’s groups), all partners go in one bulk request, and a partner whose row was not written is marked pending, not hidden (_sync_partner_lookups): no access goes through a partner’s lookup row.
    • A failed write does not fail the commit. The row is stamped error (for its version) and the hook’s exception is logged, with Elasticsearch’s reason for the first three refused documents and never their source (describe_index_error). A save outside any transaction is the exception: its write runs inline and the error reaches the caller after the commit. The GraphQL mutations avoid that: they commit in one transaction inside index_after_commit() (@commits_before_indexing), then answer with extensions.indexing = "pending" when a write failed; executeNeopsTask and abortExecution write their execution through index_execution, which does the same. deviceDelete(hardDelete: true) still writes outside the transaction and is refused while Elasticsearch is down.

    • (a) A membership mark, a client recompute or mark_rows_pending (the queryset soft delete and undelete) always sets pending, and so does a save that changes a field, moves the stored hash or leaves the row flagged, whatever the status was.
    • (b) A write for the row’s current version, stamped WHERE pk = … AND elastic_version = v on the table that holds the sync columns: the change’s own write (single or bulk), the sweep, or a populate.
    • © Also a re-index of a row that did not change (a parent refresh after a foreign key moved), and an unlock that quarantines a document or is abandoned (resync_unlock_index --abandon), which marks its entities error.
    • (d) A group the sweep rewrites because of a PendingGroupIndex row is usually synced. A rebuild sets aside, from any status, each row whose document Elasticsearch refused, at the version it sent. Both set a row aside only at the version their write sent; a row that changed since keeps its status for its own write.
    • (e) A row whose documents another write must redo is marked pending, not hidden: a partner whose lookup row was not written, a restored row’s count parents, and the count parents the sweep’s repaired rows name, which the sweep writes at the end of its run.

    Every stamp a write makes is a compare-and-set on the version its write sent, after any move past: one UPDATE … WHERE pk = … AND elastic_version = v on the table that holds the sync columns (sync_columns_model). These are _stamp_synced (persist_sync_state with hashes, and the bulk writes, 250 rows per statement), _stamp_error for the bulk writes, persist_sync_state’s own error and status-only stamps, the populate’s synced and rejected stamps, and _stamp_deleted for an archived row. A stamp that matches no row means a newer change raised the version; that row stays pending for its own write or the sweep. The sweep’s rejected is checked against the version its write sent the row’s documents at (note_version_written); a row it has no such version for, or that changed since, is left for the next sweep. Two status writes are not version-checked: the sweep’s error (after an outage it changes only pending rows, after a failure of the row’s own any row), and the error a quarantined or abandoned unlock leaves. The sweep skips rejected rows until the row changes (any change puts it back to pending), hidden or not: a rejected row that is flagged stays hidden from restricted users until it changes or a populate indexes it. A status-only stamp (write_status=True, no hashes, no lookup rows) is left to executions: persist_sync_state refuses one for a model with lookup rows.

    The permission flag is set and cleared on its own:

    stateDiagram-v2
    direction LR
    [*] --> clear
    clear --> set: access change committed
    set --> clear: synced stamp at the version written
    • Set by a Device.groups change (the devices), a changed client permission-group set (the clients), a change of Interface.device_id, Client.interface_id or Client.location_id, archiving or restoring a device, interface or client (deleted_at), and registry.mark_rows_pending for the queryset soft delete and undelete. Its other callers (a partner’s lookup row, a restore’s count parents, the sweep’s parents) pass hide=False and leave the flag as it is.
    • Cleared by _stamp_synced (persist_sync_state with hashes, and the bulk writes), the populate stamp, and _stamp_deleted for an archived row (the soft delete, the sweep), but only once its own lookup rows are deleted. rejected and error stamps leave it set.

    Versions

    • Main documents are written with version = elastic_version, version_type = external_gte (NeopsElasticDocument._prepare_action); a delete carries elastic_version + 1. Lookup rows carry the owner row’s version (lookup_write), and a lookup delete carries version + 1 (lookup_delete). An instance never loaded from the database (Model(pk=…)) is written unversioned.
    • A 409 version_conflict_engine_exception means superseded: failures_beyond_superseded drops it, lookup_write returns success.
    • Moved past. A conflict on a row still at the version it sent means the document’s version came from outside the row’s numbering (indexed before versioned writes, or a database restored behind the index). The row is raised to the held version + 1 and the write is sent once more (_past_versions_from_outside). Lookup rows follow the same rule when the write names its owner row (owner= on lookup_write / lookup_delete, _owner_moved_past); the instance stamped next follows its row to the new version (_sync_lookups_of_stamped). Bulk lookup writes follow the same rule: each LookupRow names its owner, a superseded item is rewritten on its own (lookup_write_many), and the bulk stamp follows each row to the version it is at (_follow_rows_moved_past). A row is moved past on its next write; documents and lookup rows no write reaches keep the foreign version, and what was written with it, until the upgrade rebuild.
    • Tombstones are kept for index.gc_deletes = 1h (DELETED_VERSION_RETENTION). Within that window a delayed older write cannot recreate a deleted document.
    • external_gte accepts equal versions. Count-only parent refreshes reuse the parent’s version.

    Why the highest version is complete. Elasticsearch keeps, per document, the write with the highest version (of equal ones, the last). Every write reads the row, and with it the version, before it reads the relations it lists. A change to a device’s groups, an interface or a client raises that row’s version in its own transaction (a client saved outside a transaction: right after the change), so a write that read a version at least that high read the row and its relations after the change committed. The write carrying the final version therefore reflects every committed change that raised it. Data copied from other rows does not raise it, which is why the copied fields above are not covered.

    Group bump after the commit. A membership change never locks the group row: locking it serialized every change to a large group and deadlocked two transactions taking two groups in opposite order. An advisory lock (breaks behind PgBouncer in transaction mode, or holds a transaction across the Elasticsearch call) and a global sequence (one more hot row) were rejected. Instead index_group_after_membership_change, from the hook or the sweep:

    1. raises the group’s version in a statement of its own;
    2. reads the group row and its version;
    3. reads the members;
    4. writes at the version read in step 2;
    5. deletes the change’s PendingGroupIndex rows once the write ran, also when it stamped the group error, and when the group is gone or archived (nothing is written); a write that raised (Elasticsearch unavailable, an error before the document write) keeps them for the sweep.

    Claim: once the hooks and the sweep have run, every write carrying the group’s highest version v* lists every committed change. Take such a write W and the raise R that produced v*. A change committed before R is visible to W’s member read, which follows R under READ COMMITTED. A change committed after R gets its own raise after its commit, from its hook or from the sweep reading its PendingGroupIndex row; that raise yields a version above v*, and the write after it, or the sweep’s retry of the error it leaves, carries that version, contradicting that v* is the highest.

    The argument assumes:

    • the raise commits on its own: true in the hooks, and in the sweep as long as before_lock and run_periodically never run inside an outer transaction;
    • a write that did not complete leaves a retry: a raise keeps the due rows, and an error stamp is swept. The exception is a group document Elasticsearch rejects: if the group is still at the version its write sent, the sweep sets it aside (rejected) and drops its due rows, so only the group’s next change rewrites it; if it changed since, the sweep leaves it, with its due rows, for the next run.

    The other raises of a group’s version (mark_rows_pending for deferred parents, failed partners and restores, a move past a foreign version) are increments followed by a write that reads the row before its relations, or leave the group pending for the sweep, so the claim covers them.

    Repair: the sweep

    resync_unsynced_rows(budget, grace) in backend/neops_modules/opencore/neops_core/neops/core/locking/unlock_index_sync.py, in this order:

    1. groups with PendingGroupIndex rows older than the grace, a batch of records leased at a time (_claim_due_groups): index_group_after_membership_change with UpdateType.MANUAL, so they are written with autosync off too. A record whose group is gone is dropped and not counted;
    2. rows of the signal-synced models (Device, Interface, Client, DeviceGroup; a location is swept once, as its group) with status pending or error, or with the permission flag set and any status but rejected (a synced row that is still hidden included), whose elastic_status_changed_at and elastic_sync_retry_at are both older than the grace or unset, through registry.reindex_committed_row. A live row has its own documents and lookup rows re-indexed from the database. The count parents it names itself (an interface’s device, a client’s interface, a device’s groups) are marked pending, not hidden, and written once each at the end of the run (rewrite_own_parents, write_due_parents); a group’s members are not rewritten, and a parent the run already wrote as a due group is left out. An archived or deleted row has its documents and lookup rows deleted (a document already gone counts as deleted: the bulk delete honours ignore_status=(404,)) and is stamped synced (version-checked, flag cleared) once its own lookup rows are gone too; otherwise it stays error and hidden for the next run. A rejected row waits until it changes, hidden or not.

    Rows also come pending from a partner whose lookup row a write could not rewrite, and from the parents a repair marked.

    Within each model the rows go by the later of the two times, oldest first, then by id (resync_order); the models are taken one after another. A run leases them _CLAIM_BATCH (20) at a time in a short SELECT … FOR UPDATE SKIP LOCKED transaction that moves elastic_sync_retry_at to the lease end (_claim_rows), so concurrent runs never take the same row or due record, and a run that dies leaves its rows to be taken again once the lease and the grace have passed. The whole run shares one IndexWriteBatch, with the parents deferred to its end. A failure falls in one of three classes (_unavailable, rejected_document):

    • Unavailable: any Elasticsearch error but a rejected document, or a database or operating-system error (OperationalError, InterfaceError, OSError). A pending row goes error and the run stops, so an outage costs one timeout per run; the deferred parents stay pending for the next one.
    • Rejected document (rejected_document in neops_document.py): a 400 mapper_parsing_exception, document_parsing_exception, strict_dynamic_mapping_exception, an illegal_argument_exception about the document, or a 413, for the main document or one of its lookup rows. The row goes rejected at the version its write sent (a due group’s records are dropped) and the run goes on. If the write sent nothing for the row, or the row changed since, it is left for the next sweep (left, logged at WARNING; a due group keeps its records). The log line names Elasticsearch’s reason.
    • The row’s own (bad data in a prepare_* method, a bug): the row goes error, the traceback is logged, the run goes on, and the row is retried after the grace (a due group’s records wait out the grace too).

    Each run logs one summary line; resync_unsynced_rows prints it (“Re-indexed N unsynced rows, set aside N rejected documents, left N more for the next sweep, failed on N (see the log)”). manage.py index_sync_status reports what the sweep would take now with the sweep’s own filters (rows_to_resync, due_group_records, recoverable_unlocks), and --list rejected --limit 0 names the rows set aside. It also reports an unfinished or stopped rebuild as a problem, so it exits 1 then (unfinished_rebuilds_started_at, stopped_rebuilds_started_at in its JSON). It measures the age of due group writes on created_at, which leases and failed writes move forward, so a due group that keeps failing never exceeds --max-pending-age; its group row shows as error.

    Unlocks

    An unlock whose db_updates wrote indexed data runs inside index_after_commit(). Signal-driven writes in that transaction are recorded on its work and share its batch, so both paths use one mechanism.

    1. The unlock keeps its CompositeLock row (locked=False, es_synced=False) until its writes ran and the indices were refreshed (keep_until_indexed, _finish).
    2. Meanwhile a lock that resolves entities through the index is refused with the retryable INDEX_SYNC_PENDING; an id lock is refused only when it overlaps the unlock’s entities. A lock whose search overlapped an unlock that committed or synced is refused too (refusal_if_the_index_moved, on the database clock).
    3. Once nothing has progressed for the grace period, recovery re-indexes the unlock’s entities: inline on lock requests (NEOPS_UNLOCK_INDEX_SYNC_INLINE_BUDGET, 200 entities), from the periodic task, or with manage.py resync_unlock_index. It holds a claim with a 30 s lease renewed every 5 s; the periodic run stops at its deadline and releases the claim, so the next run resumes where it stopped. Recovery re-indexes each recorded entity’s own documents and lookup rows, with the counts the database holds. The rows whose counts an unlock’s writes moved are recorded as entities of their own: a foreign key’s parents, and the partners of an add, a remove or a set(), which Django turns into remove() and add() (from the signal’s pk_set, handle_m2m_changed); they also leave PendingGroupIndex records for the sweep. A clear() records no partner: its groups get only those records, from the ids pre_clear captured (capture_lookup_m2m_clear), so they converge through the sweep, not through unlock recovery. backend/neops_modules/opencore/neops_core/neops/core/locking/unlock_membership_recovery_test.py::test_a_clear_whose_writes_were_lost_leaves_its_groups_due_and_one_sweep_rewrites_them (ES) pins a device’s groups.clear() whose writes were lost: both groups are left due, and one sweep rewrites them. A clear from the group side (group.devices.clear()) is pinned only for its after-commit write (backend/neops_modules/opencore/neops_core/tests/test_membership_index_writes.py::test_clearing_a_group_rewrites_its_former_members_and_the_group).
    4. An outage never lifts the refusal, and unlike the row sweep, neither does an error raised in this process: such an unlock refuses every searching lock, not only those on its entities, until it is retried successfully or abandoned (resync_unlock_index --abandon). An entity whose model no longer exists is quarantined at once. A document rejected NEOPS_UNLOCK_INDEX_SYNC_MAX_ATTEMPTS (3) times is quarantined: only locks resolving that entity stay refused, and the periodic task retries it every NEOPS_UNLOCK_INDEX_SYNC_QUARANTINE_RETRY_SECONDS (3600 s). A fact whose type conflicts with the shared network mapping does exactly that, and it is meant to stay loud: every searching lock is refused until the third rejection, then the locks that resolve that device or interface, until the fact is fixed and resync_unlock_index --retry-quarantined indexes it, or --clear <unlock reference> gives the documents up.
    5. Quarantine marks the quarantined entities error, which hands them to the row sweep; if Elasticsearch still refuses them there, the sweep sets them aside and index_sync_status --list rejected --limit 0 lists them. resync_unlock_index --clear gives quarantined documents up; --abandon gives a whole unlock up and marks its entities error. Synced unlock rows are pruned after NEOPS_UNLOCK_INDEX_SYNC_RETENTION_SECONDS (3600 s).

    Rebuild and upgrade

    Schema hash. manage.py elastic_index --schema-hash prints schema_hash(): a SHA-256 over the canonical JSON of the registered indices’ names, settings and mappings (after prepare_index), LOOKUP_INDICES, and INDEX_CONTENT_VERSION. index_hashes() gives each document and lookup index a hash of its own, over its definition and INDEX_CONTENT_VERSION. The build stamps use those, so a release that changes one index’s definition makes only that index stale, and a content-version bump makes every index stale.

    Bump INDEX_CONTENT_VERSION when a release changes what gets indexed without changing a name, setting or mapping: a prepare_* method’s output, a lookup_source, document ids or routing, which rows are indexed (should_index_object), what a count includes. A mapping, setting or lookup-definition change needs no bump; the hash covers it. Each bump costs every deployment one rebuild with search down while it runs. ElasticSyncConfig (the runtime sync schemas for facts and checks) is data, not code: changing it re-indexes nothing and moves no hash. Each process caches the configurations for 30 s (a save or delete through the model clears that process’s cache at once), so once that window has passed, or after restarting the workers, run elastic_index --rebuild --force; --rebuild-if-stale does not see the change, since no hash moved. A populate is enough when the change gives no field another type.

    Fact types. A rebuild gives a field the type of the first value it indexes and refuses the rows whose value does not fit, and devices and interfaces share one mapping in network. The ElasticSyncConfig schemas keep a fact or check key to one type: the index respects them, and a value that does not fit its key’s schema is indexed as null. elastic_sync_schema --analyze and the admin’s Generate schemas list “Type conflicts” (find_type_conflicts): a schema that lets more than one Elasticsearch type into one field (a type list, or anyOf/oneOf/allOf branches), or entity types sharing an index that type one key differently. The check reads schemas only, so it misses keys no schema covers, properties a schema does not name, and facts NEOPS_ELASTIC_CONVERT_FACTS indexes as one list. It exists from this release on, so it runs after the upgrade: elastic_sync_schema --analyze --sample-size -1, one type per flagged key in /admin/core/elasticsyncconfig/, then elastic_index --rebuild --force. The set-aside report below names each refused field with its row count and that remedy. A Location’s facts and checks go through the device_group schemas on save too, as the rebuild already did (entity_type_of).

    elastic_index. --create, --delete, --populate, --rebuild and --rebuild-if-stale, and sync_lookup_indices, take turns under one Postgres advisory lock (IndexRebuild.LOCK, _one_rebuild_at_a_time), reentrant per thread, held on a connection of its own, so PgBouncer in transaction mode keeps the session. A caller that waits prints “Waiting for another rebuild to finish”.

    • --rebuild marks itself (see the marker below), takes over the unfinished rebuilds before it, deletes and creates the indices, writes every document, runs sync_lookup_indices --force, and only then stamps the rows (_refill, _populate). Rebuilding core.device or core.interface repopulates both, because network holds both. A refill that returns stamps the indices it rebuilt (_stamp_rebuilt), for --rebuild as for --rebuild-if-stale, also when it set documents aside; one that raises stamps nothing.
    • Populate writes in a fixed order, since Elasticsearch types a dynamic field from the first document that carries it: by index, then by model (clients, executions, groups, then network with devices before interfaces, _in_population_order), and each model’s rows by its Meta.ordering, ties broken by pk (_in_a_fixed_order). The same database (with the same collation) therefore refuses the same documents on every rebuild, as long as no live write reaches an index while it runs. With --parallel, or more than one shard, the order is not guaranteed.
    • --rebuild-if-stale rebuilds each index whose build stamp (_meta.neops_build, stale_indices) does not name this release’s hash for that index, this cluster’s Elasticsearch version, and the epoch: when the database applied 0203_index_stamp_epoch (STAMP_EPOCH_MIGRATION), compared in UTC. Stale are a missing index, one --create just made, one a failed or killed rebuild left, every index built before this release, and every index stamped before a rollback that migrated the database back past 0203_index_stamp_epoch: the older Core wrote rows without keeping the stamps true, and the upgrade after it applies the migration again, at a new time. A planned rollback migrates the database back first, with Helm as with compose, so 0203_index_stamp_epoch is undone and every stamp is stale on the next upgrade; under --atomic that migrate-back runs from a copy of a Core pod with this release’s image, since the older image cannot undo migrations it does not know. Only a rollback that skips the migrate-back leaves the stamps current, and then the older Core cannot create entities either. A stale network, groups or clients index brings the four lookup indices with it, and a stale lookup index brings those three. So does a network, groups or clients index that is missing or unstamped (unrecorded_indices), since whatever wrote it may have changed memberships the other two still hold; one whose stamp names only another schema hash is rebuilt without the other two entity indices, though the four lookups still come with it. A standalone sync_lookup_indices --force leaves the lookup indices unstamped, so the next --rebuild-if-stale rebuilds network, groups and clients too. When none is stale it rebuilds nothing and takes the unfinished rebuilds over. It takes no --models, and fails before it deletes anything on Elasticsearch older than 8.18.
    • --create keeps an index that has the declared mapping. It replaces one missing a declared field or typing one differently (a live write’s guessed mapping, or an older release’s), up to three attempts. It ends in sync_lookup_indices, which creates and fills a missing lookup index, and when it syncs lookups it first refuses Elasticsearch older than 8.18, before it replaces anything.
    • Populate stamps rows in batches of 250, once every document and lookup row is written: each synced with the main hash of what it indexed, only where elastic_version is still the version it read, and clears the permission flag. It stamps through sync_columns_model, so a Location is stamped on its group row. It does not write elastic_relation_hash, so the row’s next hook rewrites it once. A row changed while populate ran stays pending for its own write or the sweep.
    • Set aside. Populate sets aside the main documents Elasticsearch refuses (_refusals, _stamp_rejected): each refused row is marked rejected, only where it is still at the version that was refused, and gets no synced stamp. The rebuild finishes (a --rebuild-if-stale stamps the indices) and exits with code 3 (DocumentsSetAside) after a report on stdout: the count per model; the refusals grouped by the field Elasticsearch names, each with its row count and remedy (type conflict, fields limit, other); up to 50 refused documents with Elasticsearch’s reason; and index_sync_status --list rejected --limit 0, which names every one, but no executions yet (without --limit 0 it stops at 100 ids per model and counts the rest). --populate reports the same way. A set-aside row is indexed again once a save writes it with data the index accepts (the save puts it back to pending, so the sweep takes it if that write does not run), or by the next rebuild. Any other failed write fails the run with exit code 1, sets nothing aside, stamps no row and leaves a rebuild’s marker refusing; only DocumentsSetAside exits 3. A lookup row Elasticsearch refuses is such a failure: sync_lookup_indices --force raises on it, so unlike the sweep the rebuild sets no row aside for its lookup rows.
    • sync_lookup_indices refuses Elasticsearch older than 8.18 with a CommandError (require_lookup_join), so a rebuild or up fails rather than leaving cross-entity search broken. A plain --rebuild finds out only there, after it has refilled the documents, and then keeps refusing as a failed rebuild. Its bulk writes are versioned and tolerate superseded rows. --populate-only refuses a lookup index in standard mode.
    • A query that needs a missing index, main or lookup, or a lookup index not in lookup mode, fails with SearchIndexMissing (“Search is not available right now: an index it needs is missing or being rebuilt …”) instead of creating it inside the request: list queries, their filters and ordering, aggregations and the topology query (search_error). Only Elasticsearch’s own problem text counts (index_missing): index_not_found_exception, or an ES|QL verification_exception whose reason, or one of its problem lines, starts with “Unknown index [“, “Lookup Join requires a single lookup mode index” or “invalid [..] resolution in lookup mode”. An unknown column whose name merely contains such words, facts.lookup_mode for example, is a query error reported with its reason. An entity index recreated empty raises nothing: searches miss its rows, and a criterion on its fields can fail as an unknown column. A lock refused for a missing index gets INFRASTRUCTURE_ERROR with the same text. That message, the stopped-rebuild refusal below and RelatedFieldDuringRebuild name the remedy through one constant, REBUILD_REMEDY: elastic_index --rebuild-if-stale, with its neops-docker-compose form; it never prompts, so it runs under exec -T. On compose develop, ./neops up is not a remedy: its elastic_index --create recreates a missing network, groups, clients or executions index empty, though a missing lookup index it recreates and refills. With https://github.com/zebbra/neops-docker-compose/pull/27 (open), up also runs --rebuild-if-stale, which rebuilds the missing index.
    • A versioned delete creates a missing index in standard mode, so a lookup-row delete ensures the lookup index first (_delete_lookup_row). A failed lookup write or delete, or sync_lookup_indices deleting an index, drops this process’s cached check of it (forget_lookup_index).

    Where the rebuild runs. backend/init.sh, which the core chart’s migrate Job runs, runs elastic_index --create, then elastic_index --rebuild-if-stale; it logs a warning when the rebuild exits 3 and fails on any other non-zero code (a --create that exits 1 with resource_already_exists_exception counts as success). neops-docker-compose’s ./neops up does not run init.sh: its cms-init runs elastic_index --create, and up (neops_compose/search_index.py) rebuilds with elastic_index --rebuild --force [--sync-lookups] when the Elasticsearch image changed, or the schema hash differs from the one recorded at the last up, or no hash was recorded and the core image changed. A fresh install does not rebuild. On compose develop an exit code 3 fails up, which then records no start, so every later up rebuilds again until no row is refused; https://github.com/zebbra/neops-docker-compose/pull/27 (open) moves up to --rebuild-if-stale and takes 3 as a warning. A hash read that fails must stop up: on compose develop it is still taken as “no hash” and skips the rebuild; https://github.com/zebbra/neops-docker-compose/pull/24 (open) fixes that.

    Rebuild marker. While a rebuild runs, search returns nothing or partial results. elastic_index --rebuild, and a --rebuild-if-stale that rebuilds, therefore record themselves in IndexRebuild (core_indexrebuild, backend/neops_modules/opencore/neops_core/neops/core/models/index_rebuild.py), and a thread beats for the marker every 30 s through every phase, the lookup refill included (IndexRebuild.running_now). A lock that resolves entities through search is refused with INDEX_SYNC_PENDING while a rebuild is unfinished, before the request pays for any housekeeping (refusal_during_rebuild), and so is a lock that searched while one ran (refusal_before_search, refusal_if_the_index_moved). Aggregating or sorting by a related entity’s field raises RelatedFieldDuringRebuild while a rebuild is unfinished (refuse_while_rebuilding). running_now marks a rebuild finished only when its block completes: one that raised, was killed or lost its node leaves the marker unfinished and the indices half filled, so it keeps refusing. It counts as stopped (died()) once no session holds the rebuild lock, or once its heartbeat is 5 minutes old, since Postgres can keep a lost node’s lock for hours; its refusal then names it and says to fix what stopped it and run REBUILD_REMEDY. Every rebuild, once its own marker is set, finishes every other unfinished one whatever its heartbeat (_take_over_dead_rebuilds), so a Job retry takes over at once. A rebuild with --models takes over a failed full rebuild too, without refilling the other indices, so after a failure run --rebuild-if-stale or a full --rebuild; a --rebuild-if-stale that finds every index current does the same without rebuilding. Finished rebuilds are kept an hour. The marker is set only once the delete is confirmed, so a --rebuild waiting at its prompt refuses nothing. A plain --create, --populate, --delete or sync_lookup_indices --force sets no marker. So an index --create replaces is empty, and searching locks are not refused, until the rebuild that follows marks itself; init.sh runs --create right before --rebuild-if-stale, while the new pods already serve.     • A list query whose filter raises (for example an unknown scope id) returns a GraphQL error rather than unfiltered results.
    • Rows that are pending or error without the flag (facts, discovery) stay visible with their last indexed content: stale, but not an access change.

    Before you change it

    • A new write path queues its write through _index, which runs it after the commit. registry.index_committed writes at once: call it only from code already outside a transaction (the hooks, the sweep). Never hand a document update() an instance not loaded from the database; it goes out unversioned. A GraphQL mutation that writes indexed rows runs under @commits_before_indexing (or committed_before_indexing), so it applies all or nothing and reports extensions.indexing = "pending" instead of failing after its commit; an execution is written with index_execution. A loop of index writes outside a transaction runs in one IndexWriteBatch (writing_in, @fails_fast_on_index_writes).
    • A new synced stamp is a compare-and-set on elastic_version, with the hashes, and clears the permission flag; a status-only stamp is refused for a model with lookup rows. A flagged row must wait as pending, never as synced. Write it in one UPDATE through sync_columns_model(model), never through a Location’s own manager. A new read of a row whose documents a write sends calls note_version_written, or the sweep cannot set that row aside when Elasticsearch rejects it.
    • A new indexed field. A column of the row itself is covered by the main hash and needs nothing else, unless an existing field changes meaning (then bump INDEX_CONTENT_VERSION). A field read from another row, or a new relation, is not: change detection does not see it (extend compute_relation_hash or mark the row), the source row’s change must raise this row’s version as the group bump does, and related_models will not refresh it, since it serves counts only.
    • A new relation that grants access. In the changing transaction raise elastic_version, set pending and set the flag. _PERMISSION_FIELDS sees only the row’s own columns; an m2m or a related row needs an explicit mark, as in mark_membership_pending and recompute_permission_groups. Then extend permission_pending_exclusion, get_permission_relations on the model and the document, permission_filter when the path is not <relation>.id, the partial index (permission_pending_index), and _permission_group_ids for anything that feeds a client’s groups.
    • A bulk update() on an indexed model bypasses save() and the signals. Mark the rows in the same transaction (registry.mark_rows_pending: version, pending, flag, elastic_status_changed_at; it locks the rows in key order first, so two such changes cannot deadlock, and takes hide=False for a change that revokes no access), then queue the write. index_rows_after_commit writes the rows’ documents and lookup rows but no count parents: use it when no parent count moves, otherwise queue registry.index_committed per row through _index. SoftDeletableQS._set_deleted_at is the pattern for a queryset method: change the rows by pk in a transaction, mark them there, re-index each after the commit. An update that writes only columns no document reads needs no mark (Interface.clear_neighbors); updated_at is one documents read.
    • A new lookup index needs an entry in LOOKUP_INDICES (the hash picks it up), a populate method named _populate_<index name> in sync_lookup_indices (an index without one is skipped silently), versioned writes from the registry that name their owner row (owner=, or LookupRow.owner in a bulk lookup_write_many, so a foreign version is moved past), a branch in run_lookup_sync for a new owner entity, delete handling (process_lookup_pre_delete, process_lookup_post_delete), its reader in esql_query_parser.py, and a version raise on the owner for every change to the row’s content. _lookup_document_for_model knows one lookup index per model, so a second one on an existing owner is wired in by hand, as client_interface_edges_lookup is. A lookup row a rebuild cannot write fails the rebuild; only the sweep sets lookup refusals aside.
    • A change to what a document contains without a mapping change needs an INDEX_CONTENT_VERSION bump, see Rebuild and upgrade.
    • A change to what the sweep takes goes in RESYNC_CANDIDATES and the helpers index_sync_status shares (rows_to_resync, due_group_records, recoverable_unlocks); never copy the condition. RESYNC_CANDIDATES is also the condition of the partial resync_selection_index, so changing it needs a migration like 0201_resync_selection_indexes.
    • elastic_index exit codes are a contract: 3 means only “finished, documents set aside”, which init.sh reads, and compose’s up will with https://github.com/zebbra/neops-docker-compose/pull/27; anything else is 1. A new path that writes documents sets refused rows aside with _stamp_rejected and stamps the rest only after the lookup rows are written. A new command that recreates or fills an index takes the rebuild lock (_one_rebuild_at_a_time; sync_lookup_indices takes advisory_lock(IndexRebuild.LOCK) itself, which is reentrant per thread), marks itself with IndexRebuild.running_now() when it empties or recreates an index, or searches turn silently incomplete as they do after --create, and stamps only through _refill, after the refill returned.
    • Do not run the sweep inside an outer transaction: the group bump must commit on its own.

    Database lists and search lists can disagree while rows are pending. by design; a mutation whose index writes failed answers extensions.indexing = "pending", and index_sync_status counts the rows, but lists do not say so

    A rollback that skips the migrate-back (--atomic, or a helm rollback without it) leaves this release’s migrations applied: the stamps stay current while the older Core changes existing rows under them, and it cannot create entities. open: nothing detects it; the release notes’ rollback steps run the migrate-back, from this release’s image under --atomic

    The executions index is written explicitly by the execution lifecycle, outside the after-commit queue and the sweep. A pending or error execution waits for its next state change or a rebuild, and index_sync_status --list rejected does not list executions. by design
    On a default compose install (Celery off) and on the cms-free and cms-only images, nothing sweeps periodically.     Found while writing this page, read from the code, and still open:

    Point Effect
    A hard delete marks nothing for the row itself: its document deletes, its own lookup-row deletes and the parent refresh are not retried, and a failure or a crash before them is only logged. Outside a transaction the first delete runs before the rows are deleted. Only a partner whose lookup row was not rewritten is marked pending. Unlock recovery is the exception (it re-indexes the entities it recorded). The deleted row’s document stays searchable, also for restricted users with its groups, and its lookup rows keep resolving to an id that no longer exists; the parents keep their old groups and counts. Only elastic_index --rebuild clears it; a populate does not delete orphans. When the row delete fails after that first delete, or the process dies between them, a row that still exists has lost its documents and lookup rows while it stays synced and unflagged: the sweep never takes it, and only its next change, a populate or a rebuild restores it.
    Hard-deleting a group cascades the clients’ _related_groups rows, and hard-deleting a location sets Client.location to null in bulk; neither sends an m2m_changed nor saves the client, and ClientDocument has no related_models. Client documents and client_group_edges_lookup rows keep the deleted group or location id until the client changes.
    A parent refresh after a row’s own write (_refresh_count_document_parents) logs a failure without marking anything. It runs after the child’s synced stamp, and after a hard delete. The sweep and restores mark the parents pending first. A timeout or a crash leaves the parent’s counts stale, and after a hard-deleted group the member devices’ groups too, until the parent changes.
    elastic_index --create replaces an index that misses a declared field, or types one differently, with an empty one, and sets no rebuild marker. Searching locks resolve against the empty index, unrefused, until the rebuild that follows marks itself: under init.sh the moment between --create and --rebuild-if-stale, under compose the time between cms-init’s --create and the rebuild ./neops up runs later.
    Copied fields (a device’s platform and controller, a location’s clients) are not refreshed and raise no version when their source row changes. Those documents show old values until their own row changes or a populate runs.
    elastic_index --populate or --rebuild with --no-sync-lookups stamps the rows it indexed synced and clears their permission flag without writing their lookup rows. A row flagged for an access change shows to restricted users before its lookup rows say who may see it; stale lookup rows wait for the next sync_lookup_indices or the row’s next write.
