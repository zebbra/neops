    Permissions and roles

    Everything an administrator grants in Neops, what each grant unlocks, and how a grant reaches the services that check it. It applies to a core running the permissions plugin neops_permissions_simple. Every core image ships the plugin, and the Compose and Helm deployments turn it on. Without it core allows everything, and a workflow engine in its default enforce mode refuses everything (see Without the plugin).

    Terms used below:

    • A role is a named set of grants; users hold roles, and a user’s rights are those of all their roles together.
    • A permission element is a named switch, such as workflow or network-zones, that turns a feature on for a role.
    • A device group is a group or location of devices; grants on it cover the devices, interfaces and clients in it.
    • A legacy task is a Neops 1.0 task (NeopsTask); workflows replace them.
    • A scope is a saved view in the web client: filters and dashboards over the inventory.

    How it fits together

    Core checks grants itself. Every other service gets them from the user’s access token, as <element>:<flag> strings such as workflow:read: the string worker:write is the flag write on the element worker, and is granted as exactly that.

    flowchart LR
    idp["Identity provider<br/>(role claim)"] -. "OIDC login syncs role names" .-> user
    user[User] --> role[Role]
    role --> def["Role default<br/>(all groups, tasks, scopes; creating)"]
    role --> obj["Object grants<br/>device group, task, scope"]
    role --> el["Element grants<br/>workflow, network-zones, ..."]
    def & obj & el --> core["Core checks<br/>GraphQL"]
    el --> jwt["Access token<br/>permissions: [element:flag]"]
    jwt --> engine["Workflow engine<br/>+ monitor app"]

    Flags

    Every grant sets some of three flags: read, execute and write. On a device group, execute allows running legacy tasks on its devices and write allows changing them; on an element, what each flag does is listed in the catalogue.

    Saving a grant also sets the lower flags, so the flags behave as levels: write includes read and execute, and execute includes read. That is why a token for a user granted worker:write also carries worker:read and worker:execute; nothing checks :execute on a workflow element, so the extra strings change nothing. This comes from NEOPS_PERMISSIONS_SIMPLE_IMPLICIT_PERMISSION_LEVEL (a Django setting, on by default) and happens only when a grant is saved through the admin site, GraphQL or grant_workflow_permissions. With the setting off, or for rows written in bulk, a grant keeps exactly the flags it was given, and core and the access token can then disagree about a user holding several roles (core takes the highest single grant, the token the union of flags).

    What a role holds

    Roles are created and edited in the CMS admin site at <CMS_URL>/admin/, signed in as a superuser: Role permissions is the role itself, with its name, its users and its role default; each of the other grant kinds has its own page.

    Grant Admin page Applies to
    Role default Role permissions every device group, task and scope, for each kind the role has no object grant of; also whether the role may create objects
    Device group grant Role device groups one device group, and the devices, interfaces, clients, facts, checks and configurations in it
    Task grant Role neops tasks one legacy task, and its executions
    Scope grant Role scopes one scope: list it (read) or edit it (write)
    Element grant Role permission elements one permission element from the catalogue

    How several grants combine:

    • Objects. A role with even one device-group grant is limited to the groups it names; its role default no longer covers groups at all. The same holds for tasks and for scopes. Across roles the user’s allow-list is the union. If any of the user’s roles has the flag in its role default and no object grant of that kind, the user is unrestricted for that kind.
    • Creating a device, group, interface, task, scope, location or filter needs write in the role default of one of the user’s roles. Object grants do not count.
    • Elements. If any of the user’s roles has a grant row for the element, the highest row wins, and a row with no flags is an explicit deny. If none has a row, the element’s own default applies. A role default never reaches an element.
    • No role at all sees nothing that is filtered by group, task or scope, and gets the element defaults only.

    The web client’s role editor shows a role’s default against every group, task and scope that has no grant row. That display is not what is enforced: once a role has one row of a kind, the default stops applying to that kind.

    Typical roles

    The web client always works inside a scope, so every role needs read on at least one scope: the role default covers all of them, a scope grant only the ones it names.

    Role Role default Object grants Workflow grants
    Viewer read none, or read on chosen device groups and scopes element grants workflow, workflow-execution, workflow-execution-log, worker, each read
    Workflow author read as for the viewer profile author
    Operator read as for the viewer profile operator
    Worker administrator read as for the viewer profile operator, plus element grant worker write; to manage workers without running workflows, only workflow read and worker write
    Inventory editor write none, or write on chosen device groups none; delete-facts, device-archive and tasks-archive write where their defaults were narrowed
    Administrator write none profile admin; and settings-permissions write to manage roles over GraphQL

    Permission elements

    Elements are registered by core on every start from one list in code. An element keeps the default stored in the database, edited or not: a release that changes a shipped default reaches an existing installation only through manage.py sync_permission_element --reset, which also undoes every edited default. Element names never contain :, because the colon separates the name from the flag in the token.

    Core elements

    Element Default What the flag unlocks
    settings-permissions none read: list the grant tables. write: create, edit and delete roles, add and remove their users, edit every grant, over GraphQL
    settings-permissions-add-local-user none write: create local users
    settings-permissions-add-api-key none write: list other users’ API keys and create a key for another user. The key acts as that user with all of their grants, so this is as strong as holding every other user’s roles
    network-zones read write: create, edit and delete network zones; the web client shows zone creation only with it. read has no effect
    read-password none read: the device password field returns the password instead of an empty string. Superusers always get it
    device-archive read, execute, write write: un-archive a device, delete an archived device
    tasks-archive read, execute, write write: un-archive a legacy task, delete an archived task
    delete-facts read, execute, write write: delete device, interface and group facts
    execution read, execute read: log lines of legacy task executions, outside workflow runs
    workflow-execution-log none read: every log line in the CMS logging query, workflow runs and legacy tasks alike (the engine checks the same string, below)
    workflow-execution none write: lock and unlock devices for a run. Core checks it twice for each lock: on the engine’s service account and on the user who started the run. See workflow-execution:write below
    reports none read: list reports. execute: run a report. Enterprise neops_reports module only

    Registered but checked by nothing in this release, so granting or denying them changes nothing: index, scope, search, settings, tasks, groups (legacy UI switches) and secure-gw-authentication-permissions.

    Workflow engine strings

    The engine checks these strings in the token and nothing else: there is no superuser, API-key or worker bypass, and a string must match exactly. The monitor app hides a section without its :read string and disables an action without the string that action needs, naming the missing grant.

    String Unlocks author operator admin
    workflow:read workflow definitions, the workflow schema, function blocks and their registrations ✓ ✓ ✓
    workflow:write publish a workflow definition, restore a deleted one ✓ ✓
    workflow-delete:write delete a workflow definition or a function block ✓
    workflow-execution:read runs, their jobs and the remediation ledger ✓ ✓
    workflow-execution:write start a run. Core also requires it of the user who started the run when the run locks its devices ✓ ✓
    workflow-execution-log:read logs of runs and jobs, and the log search ✓ ✓
    workflow-execution-abort:write abort a run someone else started; everyone may abort their own. The engine answers 501 to every abort in this release ✓ ✓
    workflow-execution-rollback:write roll a failed run back, which writes to devices again ✓
    workflow-execution-resolve:write mark a step as fixed by hand, retry refused CMS writes; both can release a run’s locks ✓
    worker:read workers, their function blocks, jobs and logs; the network zones the engine knows ✓ ✓
    worker:write clean up and delete workers (fails their in-flight jobs) ✓

    Continuing a rollback while resolving needs both workflow-execution-resolve:write and workflow-execution-rollback:write; filtering a worker’s logs by workflow needs workflow-execution-log:read on top of worker:read. Every workflow element defaults to no access, so a role gets workflow rights only through a grant.

    The engine itself reaches core as one service account, the user behind its NEOPS_CMS_TOKEN API key, and that account needs workflow-execution:write too. The Compose deployment mints that key for its admin user, whose seeded role carries the grant.

    Profiles

    The three columns above are the profiles of grant_workflow_permissions, which adds a profile’s grants to a role:

    manage.py grant_workflow_permissions --role <role> --profile author|operator|admin        # prints the diff
manage.py grant_workflow_permissions --role <role> --profile author|operator|admin --yes  # applies it

    With the Compose deployment run it as ./neops compose -- exec cms python manage.py …. It creates the role if it does not exist. It is additive: it never revokes a grant, so applying a narrower profile after a wider one takes nothing away. The rows it writes are ordinary element grants, visible and editable under Role permission elements. Rolling this out on an existing installation is covered in Workflow authorization rollout.

    The seeded admin role

    manage.py bootstrap_admin_role --user <user> --role <role> (run by Compose’s cms-init and the Helm hook for the installation’s admin user, with the role named by NEOPS_ADMIN_ROLE, admin by default) gives the role:

    • write in its role default, so all groups and tasks and creating objects;
    • write on the scope Global, which limits the role to that one scope: a scope created later needs a scope grant before the role’s users see it;
    • write on network-zones.

    The deployments then add the admin workflow profile. The role gets no settings-permissions, so its users manage roles and grants through the admin site as a superuser, not over GraphQL. If other users already hold a role of that name, the command only adds the user and the network-zones write, and the deployments skip the workflow profile.

    Superuser and staff

    is_superuser grants nothing in Neops except reading device passwords. A superuser without a role sees empty tables and is refused every write that is checked against device groups, tasks or scopes, exactly like any other user without a role. Django’s own flags still govern the admin site at /admin/: is_staff lets an account log in there, and is_superuser may edit every model in it, which includes every role and grant. Neither flag is in the access token, and an identity provider never changes either.

    Roles from an identity provider

    With OIDC, the role names in the token’s role claim become the user’s roles at every login: roles missing in Neops are created, and roles absent from the token are taken away. A role created that way holds no grants; it grants nothing until an administrator gives it some. So the work is the same as for local users: create the role with the name the identity provider sends, give it its grants, and let the login attach it.

    The identity provider can hand out every existing role

    A role name in the token attaches the Neops role of that name, whatever it holds. A role or group named like the seeded admin role (admin unless NEOPS_ADMIN_ROLE says otherwise) makes its members full administrators. So check the names the identity provider can send against your privileged Neops roles, and treat whoever may create, rename or assign those roles or groups in the identity provider as a Neops administrator.

    The rules are in Role sync; provider setup is in OIDC providers.

    When a change takes effect

    Change Core Workflow engine and monitor
    Element grant next request next access token (at most NEOPS_JWT_ACCESS_LIFETIME_MINUTES, default 15)
    Device group or task grant saved the process that saved it at once; every other web and Celery process within 10 minutes not in the token
    Any other grant change: scope grant, role default, a user added to or removed from a role, a deleted grant within 10 minutes in every process (the GraphQL grant mutations clear the saving process at once; adding or removing a role’s users does not) next access token
    Roles changed by an OIDC login at that login for elements, within 10 minutes for groups, tasks and scopes next access token
    User deactivated in Neops next request; refresh tokens and API keys stop working the current access token keeps working for up to 15 minutes

    To take someone’s access away, deactivate the user in Neops (Users in the admin site).

    Without the plugin

    Without neops_permissions_simple in NEOPS_PLUGINS, core allows every check, the grant tables and their mutations do not exist, and the access token carries no permissions and authz_enforced: false. A workflow engine in enforce mode then answers every gated route with 403 AUTHZ_NOT_ENFORCED. NEOPS_AUTHZ_MODE=permissive makes it skip its checks for such a core, which gives every logged-in user every engine right, rollback, resolve, deletion and worker administration included; disabled skips authentication altogether and is refused outside development unless NEOPS_ALLOW_DISABLED_AUTHZ=true. Core warns about this at start only when grants are stored.

    Where this lives in the code

    For maintainers: the element list is default_permission_elements in neops/core/auth/models.py; the combination rules and the token’s permissions claim are in the plugin’s permissions.py (neops_modules/enterprise/neops_permissions_simple/, whose README has the caching details); the profiles are in neops/core/management/commands/grant_workflow_permissions.py; the lock checks are in neops/core/schemas/mutations/lock_authz.py; the engine’s checks are the @RequirePermission decorators in neops-workflow-engine, and its route table test is test/auth/route-table.e2e-spec.ts. A new element or a new engine string changes this page.
