    neops_metrics

    Enterprise plugin that exposes a Prometheus /metrics endpoint for neops-core.

    Includes built-in infrastructure metrics (tasks, devices, executions, queue depth) and a Redis-backed custom metric API accessible from Jinja2 task templates.

    Installation

    Add neops_metrics to NEOPS_PLUGINS:

    NEOPS_PLUGINS=neops_metrics

    Metrics endpoint

    The endpoint is available at /metrics/ only when a credential is configured: a static Bearer token, or explicit anonymous access. With neither, the route is not mounted and the metrics are served only by the metrics_exporter command, which has no authentication of its own (see “Deployment”).

    Authentication

    Variable Default Description
    NEOPS_METRICS_TOKEN "" Mounts /metrics/; requests must include Authorization: Bearer <token>. Compared in constant time.
    NEOPS_METRICS_ALLOW_ANONYMOUS false Mounts /metrics/ without authentication when no token is set, and logs a warning at boot. A token, when set, still wins.

    /metrics discloses task names, scope names, fact keys and exception classes, so the backend does not serve it without one of the two. The metrics_exporter command serves the same data with no credential at all; only the network can restrict who reads it (see “Deployment”).

    Example Prometheus scrape config:

    scrape_configs:
  - job_name: neops
    static_configs:
      - targets: [neops:8000]
    metrics_path: /metrics/
    bearer_token: <your-token>

    Deployment

    Two kinds of series live on /metrics, with different multi-process behavior:

    • Shared-state metrics (everything neops_*: the collector polls Postgres/Elasticsearch/Redis at scrape time; custom template metrics live in Redis). Consistent regardless of which process answers the scrape — but identical on every replica, so scraping N replicas stores every series N times, distinguished only by the instance label.
    • In-process metrics (django_http_*, django_db_* from the optional instrument flags). Each worker process keeps its own counters and a scrape samples a random worker, so with more than one worker per instance (the image default is uvicorn --workers 4) these series are useless for rate(). Both flags therefore default to false; enable them only when running a single worker process.

    Recommended setups:

    Single backend instance (docker-compose): set NEOPS_METRICS_TOKEN and scrape the backend’s /metrics directly with that bearer token.

    Multiple backend replicas (Kubernetes): run the collector as a dedicated single-replica exporter instead of scraping the backend pods:

    python manage.py metrics_exporter --port 9100

    Deploy it as its own container/Deployment of the neops-core image (same env as the backend; it only reads — SELECTs on Postgres, health/stats on Elasticsearch, GET/SCAN/LLEN on Redis — so a read-only DB role works, and it never consumes Celery tasks). Point the scrape config at the exporter, set NEOPS_METRICS_COLLECTOR_ENABLED=false on the backend pods, and don’t scrape them.

    The exporter has no authentication. It ignores NEOPS_METRICS_TOKEN, binds 0.0.0.0:9100 by default, and serves the same task names, scope names, fact keys and exception classes as /metrics to anyone who can open the port. Make the port reachable only from the scraper:

    • on Kubernetes, add a NetworkPolicy that admits ingress to the exporter pod only from Prometheus;
    • elsewhere, keep the exporter off any network the workers or other clients share, or bind --addr to an interface only the scraper reaches.

    If you do scrape multiple replicas directly, write duplication-safe queries: aggregate with max by (...) instead of sum(...) for all neops_* series. max by is also correct for the single-instance case, so it’s a safe convention for dashboards that serve both topologies.

    Built-in metrics

    Inventory

    Metric Labels Description
    neops_tasks_total scope Active (non-archived) tasks per scope. scope=none for unassigned tasks.
    neops_executions_total status All-time executions grouped by state (running, successful, failed, partial_failed).
    neops_devices_total platform Active devices per platform short name.
    neops_scopes_total — Total number of scopes.

    Task executions

    Metric Labels Description
    neops_task_executions task, state Executions per task and state currently stored in the DB. Gauge, not a Counter — the value shrinks as retention prunes rows, so don’t use increase()/rate() on it; for execution rates prefer celery-exporter (see note below).
    neops_task_last_execution_age_seconds task, state Seconds since the last execution of that task finished in that state.
    neops_task_last_state task Outcome of the last finished execution within the lookback window: 0=successful, 1=partial_failed, 2=failed. Running/pending executions don’t affect it, and tasks with no finished execution in the window drop out — it’s a current-health signal, so stale outcomes don’t linger and state-based alerts auto-resolve. History stays queryable in the TSDB; use neops_task_last_execution_age_seconds (unwindowed) for staleness.
    neops_task_last_execution_duration_seconds task Duration of the most recent finished execution per task (dispatch to completion), within the lookback window.
    neops_task_execution_duration_seconds task Histogram of execution durations (last NEOPS_METRICS_LOOKBACK_DAYS days). Buckets: 1s, 5s, 10s, 30s, 1m, 2m, 5m, 10m, 30m, 1h.

    Task log size

    Metric Labels Description
    neops_task_log_bytes_total task Opt-in (NEOPS_METRICS_LOG_SIZE_TRACKING) — total bytes of task-log messages core hands the configured log backend (database, VictoriaLogs or Loki alike), per task, recorded at write time by a write observer on core’s logger. Counter — use increase(...[1h]) to see growth rate per task. task=unknown for writes with no resolvable execution context.
    neops_task_log_oversized_total task Opt-in (NEOPS_METRICS_LOG_SIZE_TRACKING) — count of task-log writes per task exceeding NEOPS_METRICS_LOG_OVERSIZED_THRESHOLD_BYTES. Meant to catch a task template logging full device/config output instead of a summary, before it becomes a disk problem.

    Retention

    Metric Labels Description
    neops_log_retention_enabled — 1 if the execution/log retention task is enabled, 0 otherwise. Read through core’s retention settings accessor, like the task itself.
    neops_log_retention_seconds — The configured retention horizon, in seconds.
    neops_execution_retention_backlog_total — Number of Execution rows older than the configured cutoff that are still present. Non-zero and growing means the retention task isn’t keeping up — pair with the two metrics above to distinguish “not enabled” from “enabled but failing/falling behind”.
    neops_execution_oldest_age_seconds — Age of the oldest Execution row currently present. Absent if there are no executions at all.

    Database size

    Opt-in via NEOPS_METRICS_DB_TABLE_STATS. PostgreSQL only — silently absent on any other backend.

    Metric Labels Description
    neops_db_bytes — Total on-disk size of the neops database (pg_database_size).
    neops_db_table_bytes table On-disk size per table including TOAST and indexes (pg_total_relation_size). core_execution and core_logentry are the ones that grow.
    neops_db_table_rows table Estimated live rows per table (pg_stat_user_tables.n_live_tup).
    neops_db_table_dead_rows table Estimated dead rows per table (n_dead_tup) — bloat awaiting vacuum. Expected to be non-zero on churn-heavy tables; a value that keeps climbing relative to neops_db_table_rows means autovacuum isn’t keeping up. Watch this on core_execution, where retention deletes continuously.

    Reads pg_stat_user_tables and pg_total_relation_size only — catalog and statistics views, never the tables themselves — so the cost does not grow with row count (sub-millisecond on a 67-table schema).

    Row counts are the planner’s autovacuum-maintained estimates, not exact counts. That is deliberate: a real COUNT(*) would mean a full scan of every table on every scrape, TOAST included. For growth trends the estimate is what you want anyway; for an exact number, query the table.

    Off by default because it duplicates postgres-exporter (see “Pairs well with”) where one runs, and adds roughly 3 series per table. Turn it on for deployments that have no exporter — Compose and on-prem installs, typically.

    Task failures

    Metric Labels Description
    neops_task_failure_exceptions task, exception Failed/partial-failed executions per task and neops exception code (e.g. nornir.exception.connection.timeout) within the lookback window, refreshed every 5 min. Message suffix stripped to avoid cardinality explosion.
    neops_task_failure_unknown_exceptions task, exception_class Breakdown of nornir.unknown.error by actual Python exception class extracted from the traceback (cached 5 min, lookback window applies).

    Facts

    Metric Labels Description
    neops_facts_current_total type Current (non-expired) facts per type: device, interface, group, client, common.
    neops_fact_revisions_total type Superseded fact revisions per type.
    neops_fact_last_update_age_seconds type Seconds since the most recent current fact was written, per type.
    neops_facts_by_key_total type, key Current fact count per type and key name (refreshed every 5 min).

    Elasticsearch

    Metric Labels Description
    neops_elasticsearch_cluster_status — Cluster health: 0=green, 1=yellow, 2=red.
    neops_elasticsearch_nodes_total — Number of nodes in the cluster.
    neops_elasticsearch_unassigned_shards — Number of unassigned shards.
    neops_elasticsearch_docs_total — Total documents across all indices.
    neops_elasticsearch_store_size_bytes — Total index size in bytes.
    neops_elasticsearch_sync_lag_total model, status Records not yet synced to ES per model and status (pending/error only).

    Celery

    Metric Labels Description
    neops_celery_queue_depth queue Tasks waiting in each Celery queue (celery, main, background, webhook).

    Custom

    Metric Labels Description
    neops_custom_* varies Custom metrics pushed from task templates (see below).

    Configuration

    Variable Default Description
    NEOPS_METRICS_INSTRUMENT_DB false Replace the default DB engine with django_prometheus.db.backends.postgresql to expose query count and latency metrics. Only truthful with a single worker process — see “Deployment”.
    NEOPS_METRICS_INSTRUMENT_HTTP false Install the django_prometheus request middleware (per-view request counts, latency histograms). Only truthful with a single worker process — see “Deployment”.
    NEOPS_METRICS_COLLECTOR_ENABLED true Serve the NeopsCollector (all neops_* metrics) on this instance’s /metrics. Set to false on backend replicas when a dedicated metrics_exporter serves the collector instead.
    NEOPS_METRICS_LOOKBACK_DAYS 7 Freshness window in days for all task-scoped metrics: neops_task_last_state, neops_task_last_execution_duration_seconds, the duration histogram, and the failure/unknown-exception breakdowns. Tasks with no execution within the window drop out of the current export — scraped history stays queryable in the TSDB, and state-based alerts auto-resolve. Set it to at least the schedule interval of the least frequent task you alert on: the 7-day default covers weekly schedules, which is why it is not shorter — at one day a failed weekly task disappears (and its alert resolves) while still broken. Execution counts and neops_task_last_execution_age_seconds are deliberately unwindowed — age is the staleness signal.
    NEOPS_METRICS_LOG_SIZE_TRACKING false Enables neops_task_log_bytes_total/neops_task_log_oversized_total (see “Task log size” above). Registers a write observer on core’s logger, so it covers every log backend. Fully opt-in — when false, no observer is registered. Runs on every task-log line; roll out with that in mind.
    NEOPS_METRICS_LOG_OVERSIZED_THRESHOLD_BYTES 20000 Message size, in bytes, above which a task-log write counts toward neops_task_log_oversized_total. Only relevant when NEOPS_METRICS_LOG_SIZE_TRACKING is enabled.
    NEOPS_METRICS_DB_TABLE_STATS false Enables neops_db_bytes and the per-table size/row gauges (see “Database size”). PostgreSQL only. Adds one catalog query per scrape and roughly 3 series per table; leave it off where postgres-exporter already runs.

    Custom metrics from task templates

    Task templates (Jinja2) have access to metric helpers via the neops object.

    Templates using these helpers are portable to installations without this plugin: neops-core ships the same methods as no-op stubs on NeopsHelper (writes are dropped, reads return [], the template renders normally). Enabling the plugin swaps the stubs for the Redis-backed implementations.

    API reference

    Method Description
    neops.set_global_metric(name, value, labels={}) Write a global metric. Last writer wins. No TTL.
    neops.inc_global_metric(name, amount=1, labels={}) Atomically increment a global metric. Race-safe for concurrent tasks.
    neops.del_global_metric(name) Delete all series for a global metric (reset).
    neops.set_task_metric(name, value, labels={}) Write a per-task metric. Task name auto-inferred. Scoped to the current run — the previous run’s series are dropped once a new run starts writing. 7-day TTL.
    neops.get_global_metric(name) Read all series for a global metric. Returns [{value, labels}, ...].
    neops.get_task_metrics() Read all metrics for the current task. Returns [{name, value, labels}, ...].
    neops.now() Return current UTC datetime. Useful for timing: (neops.now() - t_start).total_seconds().

    Global metrics

    Shared across all tasks. Use set_global_metric for current-state snapshots, inc_global_metric for counters that accumulate across executions.

    {# snapshot — overwritten each run #}
{% do neops.set_global_metric("queue_depth", queue | length) %}

{# atomic counter — accumulates across all tasks/executions #}
{% if edge_case %}
    {% do neops.inc_global_metric("edge_cases_total", 1, {"type": "missing_vlan"}) %}
{% endif %}

{# reset a counter (e.g. at start of a cleanup task) #}
{% do neops.del_global_metric("edge_cases_total") %}

    Per-task metrics

    Task name is inferred automatically from the Celery context. Metrics are scoped to a run: every write lands in storage keyed by the run’s Celery request id, and the first write of a new run atomically drops the previous run’s series — stale series never accumulate, and concurrent writes from parallel device threads within one run can’t lose data. Stored with a 7-day TTL.

    Pre/post-run subtasks inherit the parent’s task name. Pre- and post-run tasks execute inline within the triggering task’s run, so their set_task_metric calls are attributed to the triggered task — a subtask shared by tasks A and B reports under task="A" when A runs and task="B" when B runs, and its series are replaced together with the parent’s on the next run. Two things follow:

    • If a subtask’s metrics should be identifiable, tag them: {% do neops.set_task_metric("interfaces_up", n, {"source_task": "my_subtask"}) %}.
    • If a subtask and its parent write the same metric name with identical labels, they hit the same series and the last writer (the parent, which runs after pre-run tasks) wins.
    {% set result = neops.get_facts() %}
{% set up = result.interfaces | selectattr("state", "eq", "up") | list %}
{% set down = result.interfaces | selectattr("state", "eq", "down") | list %}

{% do neops.set_task_metric("interfaces_up", up | length, {"device": inventory_hostname}) %}
{% do neops.set_task_metric("interfaces_down", down | length, {"device": inventory_hostname}) %}

{% if down | length > 0 %}
  {% do neops.set_global_metric("has_down_interfaces", 1, {"device": inventory_hostname}) %}
{% else %}
  {% do neops.set_global_metric("has_down_interfaces", 0, {"device": inventory_hostname}) %}
{% endif %}

    Plain fake metrics Task:

    {# ── simulated measurements ──────────────────────────────── #}
{% set jitter       = range(10, 18) | random %}
{% set cpu          = range(5, 95)  | random %}
{% set memory       = range(20, 90) | random %}
{% set sessions     = range(0, 500) | random %}
{% set error_rate   = range(0, 15)  | random %}
{% set uptime_days  = range(0, 365) | random %}

{# ── derived values ──────────────────────────────────────── #}
{% set counts = {"foo": range(1, 10) | random,
                 "bar": range(1, 20) | random,
                 "baz": range(1, 5)  | random} %}
{% set total      = counts.values() | sum %}
{% set health     = 0 if error_rate > 10 else (1 if error_rate > 5 else 2) %}
{% set health_str = {0: "critical", 1: "degraded", 2: "healthy"}[health] %}

{# ── task-scoped metrics ─────────────────────────────────── #}
{% do neops.set_task_metric("jitter",       jitter) %}
{% do neops.set_task_metric("cpu_percent",  cpu) %}
{% do neops.set_task_metric("memory_percent", memory) %}
{% do neops.set_task_metric("sessions",     sessions) %}
{% do neops.set_task_metric("error_rate",   error_rate) %}
{% do neops.set_task_metric("uptime_days",  uptime_days) %}
{% do neops.set_task_metric("item_total",   total) %}
{% do neops.set_task_metric("health",       health, {"status": health_str}) %}

{% for name, val in counts.items() %}
    {% do neops.set_task_metric("item_count", val, {"name": name}) %}
{% endfor %}

{# ── global metrics (cross-run state) ───────────────────── #}
{% do neops.set_global_metric("something_high",    1 if total > 10 else 0) %}
{% do neops.set_global_metric("last_cpu_percent",  cpu) %}
{% do neops.set_global_metric("last_error_rate",   error_rate) %}
{% do neops.inc_global_metric("run_count") %}

{# ── facts ───────────────────────────────────────────────── #}
{% do neops.set_facts({
    "jitter":      jitter,
    "cpu":         cpu,
    "memory":      memory,
    "sessions":    sessions,
    "error_rate":  error_rate,
    "uptime_days": uptime_days,
    "counts":      counts,
    "health":      health_str
}) %}

{# ── debug summary ───────────────────────────────────────── #}
health={{ health_str }}  cpu={{ cpu }}%  mem={{ memory }}%  errors={{ error_rate }}  sessions={{ sessions }}
task metrics:  {{ neops.get_task_metrics() }}
run_count:     {{ neops.get_global_metric("run_count") }}

    Sample to catch exeptions

    {% set jitter = range(30, 68) | random %}
{% sleep jitter %}

 {% set r = range(0, 99) | random %}

  {% if r % 4 == 0 %}
      {# UndefinedError: access a variable that does not exist #}
      {{ this_variable_is_not_defined }}

  {% elif r % 4 == 1 %}
      {# FilterError: pipe through a non-existent filter #}
      {{ r | this_filter_does_not_exist }}

  {% elif r % 4 == 2 %}
      {# UndefinedError: call a method that does not exist on neops #}
      {{ neops.this_method_does_not_exist() }}

  {% else %}
      {# IntegrityError: set a fact with None violates NOT NULL constraint #}
      {% do neops.set_fact("crash_test_dummy", None) %}

  {% endif %}

    Debug

    task metrics:    {{ neops.get_task_metrics() }}
global my_count: {{ neops.get_global_metric("my_count") }}

    Prometheus metric names

    Custom metrics are exposed as neops_custom_<name>; any character that is not [a-zA-Z0-9_] is replaced with an underscore. The task label is added automatically for per-task metrics. Series pushed under the same name with different label sets are merged into one family (missing labels become ""), so mixing label sets is safe but best avoided for clean queries.

    Redis key layout

    neops:metric:global:{name}:{label_hash}
neops:metric:task:{task_slug}:{name}:{label_hash}

    Custom metrics are read on every Prometheus scrape. Redis must be reachable (CELERY_BROKER_URL is used for the connection).

    Pairs well with

    neops_metrics covers neops-specific context. Add these exporters alongside it for full stack observability:

    Exporter Image Port Covers
    celery-exporter danihodovic/celery-exporter 9808 Task runtime histograms, state counters, worker heartbeats
    redis-exporter oliver006/redis_exporter 9121 Memory, connections, hit rate, evictions
    postgres-exporter prometheuscommunity/postgres-exporter 9187 Query stats, locks, replication, table bloat. Its pg_stat_user_tables_* series supersede NEOPS_METRICS_DB_TABLE_STATS — run one or the other, not both.
    elasticsearch-exporter prometheuscommunity/elasticsearch-exporter 9114 Cluster health, index stats, JVM heap, GC

    Sample Prometheus scrape config:

    scrape_configs:
  - job_name: neops
    static_configs:
      - targets: [neops:8000]
    metrics_path: /metrics/
    bearer_token: <your-token>

  - job_name: celery
    static_configs:
      - targets: [celery-exporter:9808]

  - job_name: redis
    static_configs:
      - targets: [redis-exporter:9121]

  - job_name: postgres
    static_configs:
      - targets: [postgres-exporter:9187]

  - job_name: elasticsearch
    static_configs:
      - targets: [elasticsearch-exporter:9114]

    All four exporters are included in neops-docker-compose/docker-compose.yaml.

    Note on overlap: celery-exporter provides accurate event-driven task metrics (celery_task_runtime_seconds histogram, celery_tasks_total counter). The neops_task_executions and neops_task_last_execution_duration_seconds metrics from this plugin are DB-polled approximations — prefer celery-exporter for Celery task alerting and SLOs. The neops_metrics plugin adds scope context, ES sync lag, and custom template metrics that celery-exporter cannot provide.
