    Elasticsearch in Neops Core

    Reference for Elasticsearch documents, lookup edges, Lucene / ES|QL routing, indexing on save, and global query strings.

    Scope of this change: The pull request implements the architecture described here: canonical entity indices (network, groups, clients, executions), slim edge lookup indices for relationships, and joins / ES|QL for cross-entity filters so membership and interface changes do not require heavy denormalised writes across parent documents. Later phases (dual-write cutover, shrinking embedded payloads in groups / clients, retiring redundant embedded paths) are spelled out in §13 where they still apply as operational rollout.

    Authoritative detail always lives in neops.core.documents, esql_query_parser.py, and the registry — update this markdown when those change. How writes reach the index (marks, versions, the sweep, rebuilds) and which guarantees they give is in docs/architecture/search-sync.md, not here.

    1. Goals and trade-offs

    Principle Description
    Canonical data Device → primarily network (device document); group → groups; client → clients; execution → executions.
    Relationships Avoid maintaining large denormalised copies of related entities on every parent document; prefer small lookup / edge indices (IDs and minimal search keys) that are cheap to update when membership changes.
    Device changed Ideally one device document update (plus optional lookup row), not N updates to every groups document that embedded the device.
    Group changed Update groups (and location as a subtype) only.
    Device ↔ group membership Relationship / lookup updates only, not a full copy of device data into each group.
    Search Cross-entity criteria (e.g. find groups by device hostname) via **join / ES

    Trade-off: more query complexity and explicit semantics per API; fewer Elasticsearch writes on relation changes.

    2. Binding design: device ↔ group (n:m)

    Architecture:

    • device_group_edges_by_device_lookup: device → group_ids (plus minimal device keys used as join keys in ES|QL).
    • device_group_edges_by_group_lookup: group → device_ids so the n:m edge is symmetric:
    • Device side: device_id → group_ids
    • Group side: group_id → device_ids
    • Client ↔ interface as its own edge: client_interface_edges_lookup (client_id, interface_id) so client–interface filters use joins/edges instead of forcing wide client reindex on interface changes.
    • Cross-entity filters use join / ES|QL on lookup indices; large device payloads inside groups documents should shrink over time.

    Example query semantics

    devicesElastic(query: "groups.name:xyz AND devices.hostname:bla"):

    1. devices.hostname:bla — filter locally on network (device documents).
    2. groups.name:xyz — resolve matching group IDs on groups.
    3. Filter devices with a terms lookup on each matching row in device_group_edges_by_group_lookup (path: device_ids). Membership is not read from group_ids on the device document, and large group sets are not expanded into a single ids clause.
    4. AND is the intersection of both subsets.

    Aim: same search semantics as today with less write amplification through reduced denormalisation.

    Historical Elasticsearch layout (denormalised, one index per document)

    Before edge lookup indices, cross-entity search was carried almost entirely on wide primary documents: one Elasticsearch index per registered document type (network, groups, clients, executions, …), each mirroring its Django model’s search surface with deep denormalisation—related devices, interfaces, clients, and locations were embedded in parent JSON (for example devices under groups, clients under groups.location, interfaces under network devices, clients on clients with embedded interface/location payloads). Membership or hostname changes therefore tended to fan out into many parent reindexes. There were no slim index.mode: lookup tables for n:m device↔group or client↔interface edges; filters relied on those embedded structures plus network parent/child joins.

    Edge lookup indices (current)

    The same primary index names remain the user-facing search home (network, groups, clients, …). Additional indices (below) store IDs and join keys only (index.mode: lookup; ES|QL LOOKUP JOIN needs Elasticsearch ≥ 8.18). They pair with ES|QL in LuceneToESParser so relationship changes update small rows instead of rewriting large denormalised trees. index.mode cannot be changed after create: if a lookup name was auto-created as a standard index (first update() before sync_lookup_indices), LOOKUP JOIN fails with verification_exception until the index is deleted and recreated in lookup mode.

    Lookup index Role
    device_group_edges_by_device_lookup Device → group_ids (+ hostname, ip, … for join-aligned columns).
    device_group_edges_by_group_lookup Group → device_ids (symmetric n:m from the group side).
    client_group_edges_lookup Per client: client_id, interface_id, group_ids from location_id only (not _related_groups M2M); group_ids is a keyword array so the same MV_EXPAND group_ids pattern as devices applies.
    client_interface_edges_lookup Per client: client_id ↔ interface_id for interface-centric resolution paths.

    Implementation note: device_ids on the group-edge lookup is built in DeviceGroupDocument.lookup_source() (verify in code when reading this doc).

    3. Registered documents and primary indices

    All are NeopsElasticDocument under neops.core.documents. Only these five bind class Django: model = … and an Index.name.

    Document class ES index (Index.name) Django model related_models (rows whose changes refresh this document: its counts, or an execution’s snapshot)
    DeviceDocument network Device DeviceGroup, Interface
    InterfaceDocument network Interface Client
    ClientDocument clients Client —
    DeviceGroupDocument groups DeviceGroup Device
    ExecutionDocument executions Execution ProcessExecution, NeopsTask, ExecutionResult, DeviceExecution (snapshot parts)

    Location: inherits from DeviceGroup; there is no separate Elasticsearch document type only for locations. Location fields live in the same groups context as groups.

    network index: device and interface documents share the index; they differ by doc_type (device / interface) and join fields (DeviceDocument.search() / InterfaceDocument.search() filter accordingly).

    Primary index roles (summary)

    Index Role Typical content (direction)
    network Canonical devices and interfaces Device: hostname, IP, platform, group references, embedded interfaces/groups, facts/checks as mapped; Interface: names, device parent, clients, …
    groups Canonical groups (location as subtype) Group metadata, embedded devices/location/clients — target: fewer full device payloads; relations via lookups/joins (§§1–2, 6, 11).
    clients Canonical clients Client fields, embedded interface/location, … — target: slimmer interface embedding where edges cover search.
    executions Snapshot of an execution Metadata + reduced embedded relations; no follow-up reindex when device, group, interface, or client changes later (section 4).

    4. executions index (guardrails)

    Aspect Rule
    Write frequency Written essentially once around create/finish (or a fixed lifecycle) — not reindexed when Device, Group, Interface, Client, or their facts/checks change later.
    Denormalisation Intentionally denormalised for search/overview, but no deep mirroring of volatile payloads.
    Relations Reduced set: e.g. IDs, names/hostnames where search needs them — no facts, no checks, no large JSON blobs from base entities.
    Search direction One-way: execution search may resolve live devices. / groups. / interfaces. / clients.. Inventory search never queries executions (an execution result cannot add device/group/interface/client hits).
    Rationale Execution history stays stable; canonical data remains in network / groups / clients.

    ExecutionBaseAttrs includes e.g. device_execution with a device object — that object should stay slim (no facts/checks), regardless of exact mapping shape.

    Runtime: ExecutionDocument typically uses _update_type MANUAL (not the same autosync path as the other documents).

    5. Lookup indices (edges + minimum fields)

    Lookups are not full entity copies; they are join/filter tables between indices.

    Purpose Target index name Typical fields / role
    Device → groups (and join keys) device_group_edges_by_device_lookup device_id, hostname, ip, group_ids, doc_type — device → group id list for joins.
    Group → devices device_group_edges_by_group_lookup group_id, name, device_ids — symmetric n:m from the group side without full device docs in groups.
    Client → groups / interfaces client_group_edges_lookup client_id, interface_id, group_ids — explicit group edge naming.
    Client ↔ interface client_interface_edges_lookup client_id, interface_id — ES

    The registry updates these on save/M2M (process_lookup_* in neops_document_registry.py). ES|QL uses them from esql_query_parser.py (see §6).

    Document lookup_index_name() returns Notes
    DeviceDocument device_group_edges_by_device_lookup lookup_queryset / lookup_source on the document class.
    DeviceGroupDocument device_group_edges_by_group_lookup Same pattern; Location shares DeviceGroupDocument (MTI).
    ClientDocument client_group_edges_lookup client_interface_edges_lookup is maintained separately in the registry (_sync_client_interface_lookup); InterfaceDocument has no lookup_index_name but client interface edges are updated when clients/interfaces change.
    InterfaceDocument none Producer for client_interface_edges_lookup via registry helpers, not via lookup_index_name().
    ExecutionDocument none Snapshot device_ids / group_ids / interface_ids / client_ids on the executions document; live membership for groups.* uses device_group_edges_by_group_lookup.

    6. ES|QL resolution (subqueries, chains, LOOKUP JOIN)

    End-user search is still one elasticsearch-dsl Search on the active target index (network, groups, clients, …). es.esql.query is used for helper pipelines only: they return column values (IDs, interface IDs, …) that the parser turns into Q filters (terms, ids, has_child, has_parent, bool).

    No single spanning ES|QL query

    There is no one ES|QL statement that replaces the whole Lucene string across all indices. LuceneToESParser may emit several sequential ES|QL requests per user query (see tests that capture parser.esql_queries, e.g. test_esql_query_parser.py).

    LOOKUP JOIN on network

    For device-centric chains (_resolve_esql_lookup_chain_device, …), the parser evaluates ES|QL on network (often interfaces) and uses LOOKUP JOIN against device_group_edges_by_device_lookup. Join keys must line up by name and type (for example device_id as keyword in the lookup and EVAL device_id = TO_STRING(id) on the pipeline side).

    Client and group lookups

    • client_group_edges_lookup: rows are keyed by client; group_ids lists group IDs derived from location_id only. Queries typically MV_EXPAND group_ids then filter with WHERE group_ids IN (...) to match group filters, analogous to the device-side pattern even though a client usually has zero or one location group.
    • interface_id on the same lookup document is denormalised for specific parser paths (for example resolving clients.location:* from interfacesElastic / devicesElastic without chaining a second lookup in one pipeline—see _interface_ids_for_network_clients_location_presence in esql_query_parser.py).
    • client_interface_edges_lookup: resolves interface_id → client_id after interface rows have been collected from network.

    Wildcards in ES|QL predicates

    Lucene wildcards in translated ES|QL fragments are expressed with TO_LOWER(field) LIKE (see _lucene_wildcard_to_esql_like_pattern); they are not mapped to RLIKE by design.

    Global query transformers vs. parser

    ClientGlobalQueryTransformer keeps location. / clients.location. prefixes where needed so groups.* resolution does not always take the broad OR path that includes the device-group chain when a location-only path is intended. On devicesElastic, location.* is mapped to groups.* because location fields live on the group document.

    7. GraphQL and other Elasticsearch entry points

    Elastic list/aggregation fields use query, optional queryTypeGlobal, and NeopsElasticDocument.apply_lucene_query.

    GraphQL field Document Primary index
    devicesElastic DeviceDocument network
    deviceAggregation DeviceDocument network
    interfacesElastic InterfaceDocument network
    interfaceAggregation InterfaceDocument network
    clientsElastic ClientDocument clients
    clientAggregation ClientDocument clients
    groupsElastic DeviceGroupDocument groups
    groupAggregation DeviceGroupDocument groups
    executionsElastic ExecutionDocument executions

    Commented / inactive: process_executions_elastic (ProcessExecutionDocument).

    Non-Elastic lists (ORM) for the same models: devices, interfaces, clients, groups, locations, executions, facts/checks/results, … — no separate ES row in the table above.

    API / field Usage
    searchFields(index: IndexesEnum!) Derives search paths from document mappings; index enum maps e.g. devices→network, interfaces→network, groups→groups, clients→clients, executions→executions; global / globalexecutions combine sources. Implementation: neops.core.schemas.queries.search_fields.get_search_fields.
    topology DeviceDocument.search(), same Lucene pipeline as devices.
    ScopeAggregation.aggregation By aggr_type: DeviceGroupDocument, DeviceDocument, InterfaceDocument, or ClientDocument → execute_aggregation.

    Aggregations over related entities

    execute_aggregation resolves the field through aggregation_paths.resolve_aggregation, the one table of the paths each entity accepts (RELATIONS). A field of the entity’s own document is a plain terms aggregation. A related entity’s field is computed by a strategy in related_aggregations that returns what the terms aggregation over the embedded copy returned before the split: a row counts once per distinct value, the value has the related field’s type (groups.name is still analysed text, so it buckets by word; groups.name.raw by name), and buckets are ordered by count, then value. A forward link reaches an archived row (an imported client still counts under its archived interface), as Django followed it when it embedded the copy. Any other path raises UnsupportedAggregationField with the accepted paths; manage.py check_aggregation_fields lists the stored aggregations that would, scope aggregations and the web client’s dashboard cards (stored_aggregation_check).

    DirectTerms and ParsedIdTerms are one search request. The other strategies read composite aggregations page by page, 10,000 buckets a page (so search.max_buckets must stay at 10,000 or more; the default is 65,536), each composite through its own point in time (opened and closed around it, two more requests) and with allow_partial_search_results: false, so a failed shard fails the aggregation instead of dropping its documents. One point in time covers one composite, not the whole aggregation: a write between two of them can be seen by one and not the other. A strategy that joins entities, and a sort on a related field, raise RelatedFieldDuringRebuild while an IndexRebuild is unfinished: while a rebuild runs, and after one that failed or was killed part way, until a rebuild succeeds (each rebuild takes over the unfinished ones before it); the message then names the stopped rebuild and REBUILD_REMEDY. search_error(error, failed) turns an error into the GraphQL error a list, its filters, its sort, an aggregation or the topology shows: SearchIndexMissing when index_missing recognises it (index_not_found_exception, or an ES|QL verification_exception for an unknown index or one not in lookup mode); for any other error Elasticsearch answers with (ApiError), “Query failed” (or “Filter failed”) with failure_reason: the failed shard’s cause, reason or type before the generic top-level “all shards failed”, and the error’s own caused_by for a failure on the coordinating node (too many buckets, a point in time missing shards), which has neither shard nor root cause. Any other error, such as a query the parser refuses, gives its own text; a connection error or timeout raised while the search runs passes through unchanged. A dynamically mapped field (facts, checks) also costs a _mapping/field request each time its type is read: one to three per aggregation, plus one per 10,000-link batch in OwnerValues. With more than one shard, DirectTerms and ParsedIdTerms keep the terms aggregation’s shard approximation, as develop had; the joined strategies count exactly.

    A related row that has no document because it is archived is read from the database through the document’s own preparer: one query for the rows, plus one per to-many relation the preparer reads (a location’s clients), however many rows there are. terms_keys keys its values as Elasticsearch would have under the field’s mapping: numbers and booleans coerced as Elasticsearch coerces them, a date (a number too, as its text) tried against the field’s formats in order, a text value analysed once per distinct value (one _analyze request each). A value Elasticsearch would have refused is left out and logged; an object has no key of its own. The prepared source goes through the client’s JSON serializer first, so a Decimal (a location’s lat/lon) is the float Elasticsearch received. A field that only archived rows carry has no mapping in the index: it is mapped as dynamic mapping, with the document’s dynamic templates (match and match_mapping_type only), would have mapped its first value in row order, among the rows one request reads. tests/test_terms_keys.py checks each rule against Elasticsearch.

    A related entity’s dynamic fact is typed by the related index’s mapping, not by the mapping develop’s embedded copy got in the searched index from the first linked copy. Two cases differ from develop (the release notes list the paths): an IP-named fact (ip, ipv4, …, any case) is an ip in the network and groups indices and a keyword in the clients index, so paths between clients and the other entities key it differently; and a fact whose values differ in type between rows is typed by the first document of the related index that carried it, which can be a row the searched entity never reaches or, since devices and interfaces share the network index’s facts.* mapping, the other entity.

    Measured on 5,000 devices, 100,000 interfaces, 50,000 clients and 500 groups (single node, size: 10, every document matching; first run and median of three repeated runs). The requests column leaves out the point-in-time requests:

    Entity Path Strategy Elasticsearch requests First / repeated
    any own field (hostname, groups.id, name.raw on groups, …) DirectTerms: terms 1 4 / 3 ms
    interface device.id, device_id ParsedIdTerms: terms on the keyword id, parsed to a long by a runtime field 1 39 / 39 ms
    client interface.id, interface_id, location.id, location_id ParsedIdTerms 1 35 / 33 ms
    device groups.<field>, groups.location.<field> LinkedValues(many): matching devices per distinct group set (a runtime keyword), then the groups’ values 1 per 10,000 group sets, 1 per 10,000 (group, value) pairs 34 / 25 ms (groups.name)
    device interfaces.<field> ChildValues: over the matching devices’ interfaces, a composite of the values with a parent sub-aggregation, or of the distinct (value, device_id) pairs, whichever its estimate makes cheaper 3 (the total, a cardinality and a count to choose), then 1 per 10,000 values or pairs 35 / 4 ms (name), 386 / 206 ms (id)
    device interfaces.clients.<field> OwnerValues; interface to device in the database see below 596 / 482 ms
    interface device.<field> LinkedValues over device_id 1 per 10,000 devices, then 1 per 10,000 (device, value) pairs 41 / 30 ms (hostname)
    interface device.groups[.location].<field> LinkedValues; device to groups in the database as above, plus 1 query 45 / 45 ms
    interface clients.<field>, clients.location.<field> OwnerValues over the clients’ interface_id (then location_id) see below 1140 / 390 ms
    client interface.<field> LinkedValues over interface_id 1 per 10,000 interfaces, then 1 per 10,000 (interface, value) pairs 757 / 390 ms (name)
    client interface.device[.groups[.location]].<field> LinkedValues; interface to device (to groups) in the database as above, plus 1 or 2 queries 430 / 437 ms
    client location.<field> LinkedValues over location_id 1 per 10,000 locations, then 1 per 10,000 (location, value) pairs 9 / 5 ms
    group devices.<field> OwnerValues over the devices’ groups.id see below 53 / 31 ms (hostname)
    group devices.interfaces[.clients].<field> OwnerValues; device to groups in the database see below 596 / 212 ms (interfaces.name)

    ChildValues chooses by cost, not by result: both ways count exactly. The parent sub-aggregation visits every device document for each value (about 15 ns a visit), a pair costs about 3 µs (PAIR_COST_IN_PARENT_VISITS), so a field with few values (state, name) takes the sub-aggregation and id the pairs. With the sub-aggregation, interfaces.id took 19 s at 12,000 devices in review. At a million interfaces both costs rise (about 11 µs a pair, 35 to 62 ns a visit, measured in review) and the ratio stays near 200.

    OwnerValues starts with three requests (the total and two counts) and goes on from the smaller side: the matching owners or every row. From the owners: 1 request per 10,000 matching owners, then their rows in batches of 10,000 distinct links (a link that owners in two batches share is read twice). From the rows: 1 request per 10,000 (link, value) pairs of every row, all held in memory, then 1 per 10,000 owners. The side is chosen by counting owners, not links, so one group holding every device starts from the owners although its devices’ rows are many. Either way the cost grows with the related table, about 8 ms per 1,000 clients here.

    Develop answered every path in one request because the documents embedded the relation. The joined strategies grow faster than linearly at a million rows, because every composite page reruns the query over all matching rows: interfaces.id on devices took 0.2 s at 100,000 interfaces and 8.8 s at about a million (measured in review). The 30 s client timeout is reached at a few million.

    Sorting by a related entity’s field goes through sorted_search(search, ordering), which needs the search: LinkedValues.sort_field reads the related values of every document the search matches and hands them to a runtime field as script parameters (missing: _last, the lowest value ascending and the highest descending, as develop sorted by the embedded copy). It does so for every page requested, and the parameters grow with the number of linked rows. resolve_sortterm alone raises for such a key.

    Entity Ordering How First / repeated
    any own field (name, macaddress) field sort 7 / 8 ms
    interface device.id runtime long parsed from device_id 42 / 42 ms
    interface device.hostname, device.ip LinkedValues.sort_field over device_id 89 / 79 ms, 265 / 85 ms
    client interface.name LinkedValues.sort_field over interface_id 488 / 518 ms
    client interface.device.<field> as above, interface to device in the database 544 / 685 ms
    client location.<field> LinkedValues.sort_field over location_id 30 / 29 ms

    The repeated runs are answered partly from the shard request cache, which caches size: 0 requests, point-in-time pages included, until the index refreshes. Any write refreshes it, so the first run is what a dashboard pays.

    8. Lucene routing: LuceneToESParser and FIELD_CONFIG

    LuceneToESParser is built with target_index = Document.Index.name and target_type = Document.resolve_query_target_type() (neops_document.py). Prefixes devices., interfaces., groups., clients. map to local, has_child / has_parent, or ES|QL on another index via FIELD_CONFIG in esql_query_parser.py for (network, device), (network, interface), (groups, group), (clients, client).

    Device perspective — ("network", "device")

    Example: devicesElastic → network, device documents only.

    Prefix Meaning Indices / mechanism
    devices. … Local device field (often rewritten without prefix after global pass) network (device)
    interfaces. … Child interfaces network: has_child on doc_type: interface
    groups. … Search groups, map hits to member devices groups via **ES
    clients. … Client via interface chain clients via ES

    Interface perspective — ("network", "interface")

    Example: interfacesElastic → network, interface documents only.

    Prefix Meaning Indices
    interfaces. … Local interface field network (interface)
    devices. … Parent device fields network: has_parent to device
    groups. … Group via member devices groups via ES
    clients. … Client documents clients via ES

    Group perspective — ("groups", "group")

    Example: groupsElastic → groups.

    Prefix Meaning Indices
    groups. … Local group fields (name, …) groups
    devices. … Device fields of members network via **ES
    interfaces. … Interfaces via group devices network via ES
    clients. … Clients via location / group structure groups (local prefix location.clients.)

    Client perspective — ("clients", "client")

    Example: clientsElastic → clients.

    Prefix Meaning Indices
    clients. … Local client fields clients
    groups. / location. … Group via client group union groups + client_group_edges_lookup (ID-based)
    interfaces. … Interface under client network + client_interface_edges_lookup (ID-based)
    devices. … Device behind interface network via ES

    Execution perspective — executions

    ExecutionDocument uses apply_lucene_query on executions. FIELD_CONFIG has ("executions", "execution"): devices. / interfaces. / clients. run ES|QL on the live network / clients indices and filter snapshot device_ids / interface_ids / client_ids on the execution document. groups. queries the groups index and ORs group_ids with current member device_ids via device_group_edges_by_group_lookup. Unprefixed full-text uses the same relation expansion. With queryTypeGlobal, ExecutionGlobalQueryTransformer still strips fields that start with executions..

    This graph is one-way. Searching devices, groups, interfaces, or clients never queries executions and ignores executions.* field paths, so an execution result cannot add inventory hits.

    9. queryTypeGlobal: global query flow and edge cases

    When queryTypeGlobal: true, the query string is rewritten before parsing by Document.filterquery_from_global() (schemas/types.py): global paths are mapped to the local field names of the active target document. Which document is active is determined by the API (devicesElastic → DeviceDocument, and so on).

    Flow

    1. filterquery_from_global on the active NeopsElasticDocument (e.g. ClientDocument) rewrites user-facing field paths into canonical paths.
    2. LuceneToESParser (built with that document’s target_index and target_type) maps those paths to joins / ES|QL. Subqueries use the correct columns per index; there is no second “global” pass inside the parser.

    Further normalisation and history: module global_query_normalize.py.

    groupsElastic and clients.location

    For clients.location:* (prefix clients + field location), the parser builds the embedded predicate on location.clients.macaddress (see default_field in FIELD_CONFIG), not on the unmapped location.clients.location. Otherwise the first OR branch never matches group documents, and a combination with groups.id can look empty even when the location_id-based path on the clients index would match.

    groupsElastic, devicesElastic, and interfacesElastic

    The same graph path …groups.devices.interfaces.clients is rewritten in the respective *GlobalQueryTransformer classes before devices. / interfaces. stripping to clients.interface_id (existence) or clients.<leaf>, so interfaces.clients (invalid ES|QL column) is never produced.

    clientsElastic examples

    User input (global) After normalisation (canonical)
    groups.devices.interfaces.clients: * interface_id: *
    interfaces: * / interface: * interface_id: *
    clients.location: * location_id: *

    Relational filters keep their prefix, e.g. groups.id, interfaces.name, devices.hostname.

    The raw condition interface: * (without _id) is not expected after the client transformer; if it remains in the string, validate_no_ambiguous_client_global_fields fails with an explicit error.

    Extending global behaviour

    • Shared regex building blocks: global_query_normalize.RE_*
    • Single-token fields on the clients index: coerce_clients_bare_field_name / parser hook _coerce_bare_field_for_target_index

    11. Residual embedded denormalisation and follow-up work

    This PR moves query and lookup logic onto edge indices and ES|QL. Some embedded denormalisation in groups / clients may still exist in mappings or documents until a later reindex (see §13 Phase 4). The table below is historical → direction of this work, not “two competing designs”.

    Area Legacy pattern Direction in this work
    groups.devices.* in groupsElastic Often resolved locally on denormalised devices[] inside groups Prefer edge + network / device-group lookup; group hits driven by IDs / join
    Device in many groups Many groups docs could embed full device payloads One device doc on network + lookup rows; membership updates without copying full device into every group
    Group-side lookup group_id, name only device_ids on device_group_edges_by_group_lookup for symmetric n:m with group_ids on the device-side lookup
    Client ↔ interface Interface payload embedded on clients client_interface_edges_lookup + joins so interface edits do not force wide client reindex

    13. Migration plan (high level)

    Phases may overlap with this PR depending on how you ship; keep the sequence for data and query safety.

    1. Phase 1 — Lookup indices: Ensure indices with keyword IDs and index.mode: lookup (required for ES|QL LOOKUP JOIN; mode cannot be changed after create). Group edge includes device_ids. Backfill from DB (manage.py sync_lookup_indices). If an index was auto-created as standard (e.g. first autosync upsert before the command ran), the next sync_lookup_indices recreates it in lookup mode; --force always rebuilds. --populate-only refuses a standard-mode index.
    2. Phase 2 — Operational hardening: Integrity checks (edge counts, spot checks device↔group, client↔interface); monitor sync latency/errors on process_lookup_* / refresh_lookups_for_post_save.
    3. Phase 3 — Query layer: Parser/ES|QL use lookup indices as documented in §6 and §8; groups.* / clients.* filters use edge joins where applicable; feature flag if needed for risky path changes.
    4. Phase 4 — Shrink denormalisation: Reduce/remove device payload in groups and interface payload in clients; reindex with new mapping.
    5. Phase 5 — Cleanup: Remove redundant embedded search paths once parity is proven; smoke queries and aggregation comparison; runbook for rebuild/rollback.

    Rebuild

    uv run python manage.py elastic_index --rebuild --force \
  --models core.device core.interface core.devicegroup core.client

    network holds both device and interface documents, so rebuilding either model deletes that index and repopulates both (the command says so). The lookup indices are rebuilt in the same run whenever a lookup-backed model is selected (--no-sync-lookups skips them). If populating the lookups runs out of memory, refill them on their own with sync_lookup_indices --populate-only --batch-size 500.
