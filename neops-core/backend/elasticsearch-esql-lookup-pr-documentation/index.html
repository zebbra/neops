    PR documentation: Elasticsearch parent/child, ES|QL & lookup indices

    Baseline: origin/develop @ 06317f672 (merge including hotfix #2192)
    Verification: branch state re-checked in workspace; pytest for ES|QL/lookup: 38 passed (2026-04-05)

    This document summarizes architecture, index usage, update paths, ES|QL query translation, model consistency, efficiency, and review findings.

    1. Executive summary (purpose of the PR)

    • Primary indices (network, groups, clients, …) remain the source for user search; additional lookup indices (index.mode: lookup) materialize edges (device↔group, client↔interface, client↔location/group) so ES|QL LOOKUP JOIN and server-side filter resolution are possible.
    • Lucene-style query strings are translated in LuceneToESParser into elasticsearch-dsl Q objects (has_child, has_parent, terms, ids, …) and, where needed, ES|QL subqueries; ES|QL returns ID sets for the actual search.
    • Sync control: besides elastic_sync_hash, elastic_relation_hash / elastic_relation_synced_at (migration 0174) track relational changes; update_with_status coordinates the main document, lookups, and DB status.
    • UpdateType.AUTOSYNC_CELERY is normalized to AUTOSYNC_DIRECT in the registry (compatibility; no separate Celery path for this distinction anymore).

    2. Index landscape (which index for what, how it is updated)

    Index Role How it is updated
    network Parent/child: doc_type=device / interface, join field django-elasticsearch-dsl Document.update; registry sync_main_documents / flush_cache
    groups DeviceGroup including embedded location (MTI: Location shares DeviceGroupDocument) same as above
    clients Client master data same as above
    device_group_edges_by_device_lookup Per device: device_id, group_ids, hostname, ip, doc_type DeviceDocument.lookup_* → NeopsElasticDocument.lookup_upsert_with_detect_noop; after successful main sync in update_with_status / flush_cache; bulk: manage.py sync_lookup_indices
    device_group_edges_by_group_lookup Per group: group_id, device_ids, name same pattern via DeviceGroupDocument
    client_group_edges_lookup Per client: client_id, interface_id, group_ids (location→group only) ClientDocument + registry; see semantics below
    client_interface_edges_lookup Per client: narrow edge client_id ↔ interface_id explicitly in registry (_sync_client_interface_lookup); on client save only if interface_id is in _es_changed_fields or full refresh

    Management:

    • python manage.py sync_lookup_indices — creates lookup indices (ES ≥ 8.16 because of index.mode: lookup) and populates them fully.
    • python manage.py elastic_index … --sync-lookups — after populate / rebuild, optionally runs sync_lookup_indices --force.

    3. Models ↔ documents ↔ lookup (handling consistency)

    Django model Document Primary index Lookup Notes
    Device DeviceDocument network (device) device_group_edges_by_device_lookup lookup_queryset: prefetch_related("groups"); exactly one lookup per model (via document API).
    DeviceGroup DeviceGroupDocument groups device_group_edges_by_group_lookup Same pattern; Location shares the same document via elasticsearch_mti_models.
    Client ClientDocument clients client_group_edges_lookup + client_interface_edges_lookup Only intentional deviation: two physical lookup indices; logic in refresh_lookups_for_post_save / _sync_client_lookup.
    Interface InterfaceDocument network (interface) none Relation hash in compute_relation_hash drives skip/write in device/client context; no lookup row for interfaces.

    Shared convention (where a lookup exists): lookup_index_name, lookup_doc_id, lookup_queryset, lookup_source on the document class; the registry picks the first registered NeopsElasticDocument with a non-empty lookup_index_name() via _lookup_document_for_model.

    Deliberately split semantics:

    • client_group_edges_lookup.group_ids: only client → location_id (DeviceGroup). This does not mirror the _related_groups M2M.
    • Device/group membership for search: device_group_edges_* and ES|QL chains over network + LOOKUP JOIN.

    4. Behavioral changes (short, for review & operations)

    • update_with_status: writes the main document when main hash or relation hash changed (should_write_main); then optionally lookups (refresh_lookups), then persist_sync_state with both hashes (on lookup failure: ERROR status).
    • flush_cache: single pass; writes instances when hashes change; then sync_lookup_documents for Device, Client, DeviceGroup and persist_sync_state.
    • M2M device↔group: update_with_status(..., skip_change_detection=True, refresh_lookups=False) plus process_lookup_m2m_changed — avoids duplicate lookup upserts in the same event.
    • Client._related_groups.through: skipped in the M2M handler — client_group_edges_lookup follows location, not this M2M (see comment in neops_signal_processor.py).
    • Deleting DeviceGroup: process_lookup_pre_delete captures device IDs; after delete, affected device lookups are upserted again (group removed from edge lists).
    • Document IDs: parse_meta_id and ES|QL paths support prefixed IDs (device-12, …) alongside plain numeric legacy IDs; group queries use bool should on both shapes (_resolve_groups_from_group_ids / client ID resolution analogous).

    5. ES|QL & query parsing (esql_query_parser.py)

    5.1 Flow

    1. Lucene string → luqum AST → LuceneToESParser._visit*.
    2. Key: (target_index, target_type) from apply_lucene_query (e.g. DeviceDocument → network / device).
    3. FIELD_CONFIG maps the first path segment (devices, interfaces, groups, clients, …) to a strategy.

    5.2 Strategy types (overview)

    Type Meaning
    local Field on the current search index
    join_child / join_parent Parent/child on network
    esql ES
    esql_to_join ES
    esql_via_parent ES
    esql_lookup_chain_* ES
    group_clients_location_and_clients_index OR: embedded location.clients.* on the group or path via clients index → client_group_edges_lookup
    esql_lookup_chain_client_groups_location_only filter groups, then only client_group_edges_lookup (no device-group lookup path)

    5.3 Multiple indices in one user query

    There is no single ES|QL query spanning all indices for the final search. Instead:

    1. The main search stays an elasticsearch-dsl search on the target index (network, groups, clients, …).
    2. Certain AST nodes trigger one or more ES|QL requests; results are embedded as Q filters (IDs, terms, has_child, …).
    3. Chains (e.g. group → devices → interfaces → clients) cause several sequential es.esql.query calls (see test_esql_query_parser.py, which inspects parser.esql_queries).

    Join requirement: LOOKUP JOIN needs the same column names on both sides (e.g. device_id as keyword in the lookup and EVAL device_id = TO_STRING(id) on network).

    Wildcards in ES|QL: Lucene wildcards become TO_LOWER(field) LIKE via _lucene_wildcard_to_esql_like_pattern (wildcards intentionally not mapped to RLIKE).

    5.4 Global transformer vs. parser

    • ClientGlobalQueryTransformer: paths location.* / clients.location.* keep the location. prefix so that in the clients context resolution does not take the broad groups.* OR path with the device-group chain.
    • Device context: location.* is mapped to the groups prefix in the parser (location lives on the group).

    6. Structure: Django/ES model vs. search path

    • Primary ES indices: hierarchical (parent/child on network), denormalized (groups.location, embedded clients), flat clients documents.
    • Lookup indices: edges only for joins and ID resolution — not a full mirror of all searchable fields.
    • API layer: search_fields / _canonicalize_global_field_path collapse equivalent paths so UI and parser share the same semantics.

    7. Efficiency (queries & updates)

    Positive:

    • Lookup writes: detect_noop=True on updates.
    • No generic update_related fan-out; cross-model denormalization is explicit (MTI, reindex, parser).
    • M2M: separate phases for main doc and lookups reduce duplicate work.
    • refresh_lookups_for_post_save for client: interface lookup only when interface_id changes (via _es_changed_fields), fewer ES calls otherwise.

    Cost / observation:

    • Complex global filters can trigger many ES|QL round trips per search (chains over network + multiple lookups + groups/clients).
    • After elastic_index bulk, _update_sync_status may still set elastic_sync_hash primarily; a later update_with_status may once detect relation changes again — see earlier review note; optionally align elastic_relation_hash in the bulk path later.

    8. Code clarity

    • esql_query_parser.py: module docstring + FIELD_CONFIG comment; many _resolve_* methods — section 5.2 table is the short map.
    • neops_document_registry.py: refresh_lookups_for_post_save is the canonical lookup sync entry; process_lookup_post_save / sync_lookup_documents are aliases (backward compatibility).
    • dispatch_lookup_sync: thin wrapper around run_lookup_sync — intentional for tests/mocking; not dead code.

    9. Unused code & cleanup opportunities

    Finding Assessment
    Commented _update_type / __init__ blocks in neops_document.py, device.py, device_group.py, client.py No runtime impact; optional removal for readability.
    PreferredDocumentUpdateType.AUTOSYNC_CELERY / is_auto_sync_celery() Still referenced in sync_main_documents (branch for non-Neops docs); for NeopsElasticDocument, effectively DIRECT after registry normalization.
    _dispatch_lookup_for_instance Used in process_lookup_post_delete — not dead.

    Do not treat as a “special case” anymore (verified, intentional):

    • Two client lookups are an architecture choice, not a temporary hack.
    • Legacy and prefixed IDs in ids queries are a safety net during mixed index states, not “legacy-only” support.

    11. PR verification summary

    • Consistency: Device, DeviceGroup, and client follow the same document-backed lookup pattern; Client is documented as the exception with two lookups and _es_changed_fields optimization for client_interface_edges_lookup.
    • Index usage: primary indices for search and denormalization; lookups only for joins and ID chains in filters resolved via ES|QL.
    • Multi-index queries: the final query is always one DSL search on the target index; extra access happens through embedded ES|QL helper queries — for performance reviews, watch LuceneToESParser.esql_queries length per request.
    • Unused: no significant dead registry/parser logic; at most cosmetic commented leftovers in document classes.
